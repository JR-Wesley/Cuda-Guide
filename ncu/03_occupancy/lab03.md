# 实验 03｜线程块怎样占用 SM：先做资源预算，再看 Occupancy

## 为什么改变 block 大小不一定更快

把 257 份作业分给每组 128、256 或 512 人，需要的组数不同，但有用工作仍是 257 份。GPU 中，**kernel（内核）**是 GPU 函数，一次 **launch（启动）**提交许多**线程**各自执行函数；线程是有自己编号和数据的一份任务。线程先组成 **block（线程块）**，所有块组成 **grid（网格）**。**SM** 是 GPU 中接纳线程块的计算单元，一个普通块不跨 SM，一个 SM 可接纳多块。

每块还要占用有限资源：**槽位**是保留执行状态的位置，**寄存器**保存每线程的中间值，**共享内存**是同块线程可使用的片上工作区。例如各线程暂存自己的乘积会用到寄存器，块内暂存一批可复用数据则可能用共享内存。已被接纳、资源已保留且尚未退出叫**驻留**；资源不足时不能再接纳下一整块。本课只计算这个容量上限，不从容量直接推断下一条指令能否执行。

本课要把这个因果链拆开验证。先用每线程只算一次乘法的程序，保持输出和总工作量不变，只改变线程怎样分块，手算资源上限再对照报告。接着换成每线程反复做乘加的程序，让线程保存多条计算链的中间结果，检查编译后的寄存器需求是否改变，以及它是否改变理论驻留上限；链数多不保证寄存器数必然增加。实验值得做的地方不在于找一个通用的最佳 block，而在于学会解释：一个占用率数字由什么资源限制，又为什么未必决定完成时间。

配套阅读 [lec03](lec03.md) 第 1–4 节，先理解硬件分层、资源需求和理论上限；实际驻留与性能权衡另读 [lec04](../04_warp_scheduling/lec04.md) 第 1.0、9.1–9.2 节。本课的资源计算是主线；FMA 补例也先分析中间值与资源需求。运行时指标只在文末列为第四课接续问题，不要求在本课采集或诊断调度状态。重点不是追求百分比最大，而是解释**这个上限由什么决定，是否真的影响完成时间**。


## 1. 先手算网格，分清分组和工作量

先认识主实验实际计算的内容。`vector_mul` 接收两个浮点输入数组 a、b，生成 N 个乘积 c；本课连续读取，也就是第 i 项输出为 a[i] 乘 b[i]。例如 N=4 时，a 为 `[0, 0.125, 0.25, 0.375]`，b 全为 2，c 就是 `[0, 0.25, 0.5, 0.75]`。这里没有求和，也没有用上次输出继续计算，所以同一输入无论分成多少块，答案都应相同。

每个线程先从块号和块内编号算出全局 i；i 小于 N 才读两个输入、做一次乘法、写一个输出。**Host / Device** 指 CPU / GPU 两侧；CPU 提交 GPU 任务通常异步返回，即 GPU 尚未完成时 CPU 也能继续运行，使用结果前须等待相关计算完成。Host 的 `run_vector` 在 CPU 生成输入，分配并上传 GPU 数组，以 `ceil(N/block)` 个块启动 kernel，下载结果后用 `(i%1024)*0.25` 检查每一项。这里 `ceil(N/block)` 表示 N 除以每块线程数后向上取整，不能丢掉余下元素；例如 `ceil(257/128)=3`。改变 block 只会重新分配这些编号到各块，不应改变有效线程做的算术。

正因为算法这么简单，它适合先隔离“分组”这个变量：如果三种 block 的结果不同，应先查正确性；如果结果相同而占用率或耗时不同，才讨论块如何占用 SM。它不刻意制造寄存器压力，因此也可能得到三种配置资源上限相同的结果，这不是实验失败。

**目的与代码：** 读 [main.cu](kernels/main.cu) 的 `use_fma=false` 和 n/block/stride，再读 [vector_mul](../kernels/vector_multiply.cuh)。本步只阅读推导，无需执行。

默认 N=16、block=256、stride=1（相邻有效输入间隔为 1 个元素，即连续读取），只有一个块，16 个线程有效；输出 `c[i]=(i%1024)*0.25`，即 `0..3.75`、间隔 0.25。改 block 只改变分组，不改变输出。

**Warp（线程束）**是块内每 32 个线程组成的执行群组，也是驻留容量的计数单位；不满 32 个也要单独一个 Warp。比如 128 线程为 4 Warp，33 线程需要 2 Warp。先把 N 想成 257，填写下表：

| block | 每块 warp 数 | grid=ceil(N/block) | 最后一个块的有效线程 |
|---:|---:|---:|---:|
| 128 | 4 | 3 | 1 |
| 256 | 8 | 2 | 1 |
| 512 | 16 | 1 | 257 |

**原理：** 线程编号为 `blockIdx.x*blockDim.x+threadIdx.x`，三个量依次是块号、每块线程数、块内线程号；`i<n` 避免尾块越界。warp 上下文是保留这一组任务执行状态的资源；分配了它不等于所有 lane（warp 内线程位置）都有有效输出；不能把尾块无效线程当成未分配硬件资源。

**检查：** 如果结果预测随 block 改变，先检查把全局 i 错看成块内线程号的问题。N=16 的整卡工作太少，本课不拿它评价稳定吞吐或占用瓶颈。

## 3. 先在纸上推导“能驻留多少块”

边界核对确认分块没有改变答案后，再问同一 SM 能装下几块。网格中的块并不是一次全部驻留：每接纳一个块，就要为整块保留相应的线程与资源，余下预算不足以容纳下一整块时，只能等已有块退出。因此资源预算需要按“整块”取整，而不能只比较总线程数。这个预算给的是可驻留上限；网格太小或执行接近尾声时，实际工作仍可能填不满它。

**目的与代码：** 对照 kernel 的块大小与资源使用，可参照 lec03 第 3.2–3.4 节；下面也给出完整简化预算。寄存器数量由编译器分配，不等于源码变量数；临时值可能被删除或复用存储，64 位值还可能占多个 32 位寄存器。本课寄存器按 32 位的“个数”计，共享内存按字节计。**静态**共享内存在编译时确定，**动态**共享内存在启动时额外指定，两者都要计入。

忽略分配粒度的简化模型：每块 `Wb=ceil(block/32)` 个 warp、每线程 R 个寄存器、每块 S 字节共享内存，则驻留块数受以下各项最小值约束：

```text
硬件块数上限
floor(每 SM 线程上限 / block)
floor(每 SM warp 上限 / Wb)
floor(每 SM 寄存器预算 / (R * block))
floor(每 SM 共享内存预算 / S)  （S=0 时不由该项限制）
```

这里 `ceil` 向上取整，`floor` 向下取整；每个比值都是“每 SM 容量 ÷ 每块需求”，得到块/SM，最后取所有上限的最小值，因为资源必须同时够用。例如寄存器预算为 65536 个、每块 256 线程、每线程 64 个，则寄存器只允许 `floor(65536/(256*64))=4` 块。

**理论 Occupancy（理论占用率）**约为 `驻留块数 * Wb / 每SM最大warp数`。分子分母均为每 SM 的 Warp 数，相除无单位，乘 100% 得百分比，不对运行时间取平均。例如 4 块、每块 8 Warp、硬件上限 64 Warp，就是 50%。真实资源还按**分配粒度**预留，例如需求 257 单位但只能按 256 的整份分配，就会占 512 单位；此外还有分区约束（某局部资源不足不能靠其他分区余量补足）。最后用对应架构工具核对，不能只套这个理想公式。

**纸上例子，不是设备数据：** 假设某 SM 上限为 48 warp、1536 线程、16 块，寄存器/共享内存不限制。block=128 时线程与 warp 限制为 12 块，得到 48 warp；block=256 为 6 块，也是 48 warp；block=512 为 3 块，仍是 48 warp。因此三种 block 可以有相同的 100% 理论占用率。实际 GPU 不能照抄这些假设数。

**理解检查：** 若另有块数限制为 8，128 线程只能驻留 32 warp。由此解释为什么占用率会按资源取整出现阶梯变化，而不是 block 翻倍占用率必翻倍。

## 4. 主实验 A：只改变 block，先普通运行再采集

纸上预算还不能回答时间问题。现在增大 N，让网格提供更多块，再把同一批乘法分别装进 128、256、512 线程的块：块越大，每块消耗越多，但总块数也更少，几个约束可能恰好抵消。我们要检验的不是“块大一定好”，而是配置是否改变了静态资源上限、哪个约束最先限制，以及普通计时是否同时改变。本课不进一步用调度状态解释时间差；即使时间变化，也先保留待第四课验证的原因假设。先看 LaunchStats，正是为了确保后面的比较确实对应这次重新分组。

**目的：** 保持同样的乘法工作，核对分组与资源上限；普通时间另记作背景，不把相伴变化当成因果证明。

先确定计时边界：共享 [time_kernel](../kernels/common.cuh) 先预热 10 次（计时前先运行以改变初始化、缓存和频率状态），再在两个 **CUDA Event** 之间提交 20 次启动。Event 是插入 GPU 有序工作队列的时间标记，等结束标记完成后读区间时差，再除以 20。例如区间 0.4 ms，批量平均为 0.02 ms/次；1 ms 是千分之一秒。平均不含分配、拷贝、核对，可能含提交间隙。**Duration** 是 NCU 报告中采集对象的时长，与普通 Event 时间分列；NCU 下打印的 Event 时间不是独立 benchmark（基准测试）。保留三次普通运行原始值及范围，不只留最快一次。

把入口设为 `use_fma=false, n=262144, stride=1`，先 block=256。重用步骤 2 的 nvcc 命令编译，再在本课目录执行：

```bash
./build/lesson03
./build/lesson03
./build/lesson03
ncu --list-sections
ncu --section LaunchStats --section SpeedOfLight \
    --section Occupancy \
    --kernel-name-base function -k vector_mul -s 10 -c 1 \
    --replay-mode kernel --cache-control all --clock-control base \
    -o log/vector_mul_b256.ncu-rep ./build/lesson03
ncu --import log/vector_mul_b256.ncu-rep --page details
```

**Section** 是围绕一个分析问题组织的指标组，`--section` 分别选择启动资源（LaunchStats）、性能概览（SpeedOfLight）、占用率（Occupancy）；这次只读 Occupancy 的理论值与限制资源，报告可能附带的动态字段不作为本课分析要求。`--kernel-name-base function -k` 按函数基础名过滤；`-s 10 -c 1` 只采第 11 次匹配启动，不改变应用的 30 次启动。**replay（重放）**是分析器为收齐指标而重复执行目标工作，每轮采集叫 pass，不等于应用自己多提交一次。all/base 是工具主动清缓存/请求基础时钟控制的选项，不保证每次读取都到显存，也不表示权限或频率一定可控；时钟频率表示硬件每秒经历多少周期，支持情况以工具输出为准。`-o` 导出、`--import` 读报告，`--page details` 显示分组详情；采集前确认没有同名文件，需要保留则先明确另存，不强制覆盖。

随后只改 block 为 128，再为 512；**每次重编 → 普通运行核对 → 重复计时 → 采集**，报告分别改为 `vector_mul_b128.ncu-rep`、`vector_mul_b512.ncu-rep`，不可覆盖混用。预期 grid 分别为 2048/1024/512（对应 block=128/256/512），输出完全相同。

**按顺序看什么：** `Registers/Thread` 是每线程寄存器数，`Shared Memory` 是共享内存用量；`Theoretical` 表示理论上限。`SpeedOfLight` 中的吞吐百分比以工具定义的硬件处理能力为参照，不是占用率，也不直接证明计算或访存瓶颈。

| 证据 | 记录内容 | 能回答什么 |
|---|---|---|
| LaunchStats | grid、block、Registers/Thread、Shared Memory | 配置是否真的改对，编译资源是多少 |
| Occupancy | Theoretical、限制资源 | 静态预算是否吻合，哪项资源先限制 |
| 普通 Event / 报告 Duration | 分别记录，不混在一列 | 真实重复调用基线与受控采集各自如何变化 |

**解释与异常：** Theoretical 计算的是已编译资源与启动参数允许的上限，不保证运行时一直填满。A 的三种配置可能理论占用率相同；这仍然是有效观察。无报告先查过滤器/权限/退出信息；grid 不符先查重编与输出配置；不同名报告也必须核对实际配置，不能只信文件名。

## 5. 补例 D：固定 FMA 总数，只改变独立链数

乘法每个线程只需很少的中间数据，改变 block 未必能显露寄存器约束。为继续研究资源与并行性的关系，补例改成反复更新数值：FMA（融合乘加）`fmaf(x,a,b)` 计算 `x*a+b`，乘与加合起来只舍入一次，即只在合并计算的最终结果上按浮点格式取可表示的值，而不是乘完先取一次、加完再取一次。这里不是数组逐项相乘，kernel 的输入是 N、每线程总乘加次数、乘数 `1.0001f` 和加数 `0.0001f`；初始数值由线程编号 i 和链编号 j 生成，输出仍是每线程一个数 `out[i]`。

用一个小例子看“链”的含义。线程 i=0 的第 0 个初值是 `0.5+1/256=0.50390625`。若总次数为 8、只有一条链，就连续更新这个 x 八次：第一次约为 `0.50405664`，第二次必须读取第一次的结果，直到第八次才能输出。这里的近似值只帮助理解，实际按 float 的融合乘加舍入。若改为四条链，四个初值为 `0.5+(j+1)/256`，各更新两次，最后把四个结果相加写入 out[0]。一条链内部前后相依，四条链的递推彼此独立；不过末尾求和仍有依赖，且四链答案本就不同于单链答案。

每个有效线程独立完成上述过程，越界线程返回，没有线程间通信。Host 的 `run_fma` 只需分配 GPU 输出数组，不上传 a、b 数组；它以 `ceil(N/block)` 个块传入这些标量参数（每项是单个数，不是数组）并重复启动，下载 N 项输出，再在 CPU 按相同初值、递推次数和求和顺序逐项重算。这样核对的是每种链数自身的算法，不是要求不同链数输出相等。

增加独立链，需要同时保留更多互不相依的中间值，可能消耗更多寄存器，从而减少资源允许的驻留 warp。这是本课要核对的静态假设；多个独立计算能否补偿较少的驻留工作、为何改变时间，属于第四课的执行分析。A 若没有明显寄存器差异，不要硬造趋势；切换 A→D 是换算法，**不是单变量加速比较**。理解这个新计算后，再读 [fma.cuh](../kernels/fma.cuh) 的 `fma_initial → fma_chain → run_fma`。

先设 `use_fma=true, n=16, block=256, chains=1, total_fmas_per_thread=1024`，按步骤 2 重编运行，检查 `Check: PASS, checked=16, mismatches=0`。CPU 按同样的 fmaf 次序核对全部结果；要求两侧有限（不是无穷大或非数 NaN），且绝对误差 `abs(GPU-reference)` 不超过 `1e-5 + 1e-4*abs(reference)`。其中 `abs` 取绝对值，`1e-5` 是绝对容差，`1e-4` 是乘以参考值大小的相对容差，例如 reference=2 时允许误差为 0.00021。不同链数输出不同，各自对各自参考值检查。

通过后只把 n 改为 262144 并重编，后续固定它。依次只改 chains=1/4/8，每次重编、普通运行三次并核对；每线程总 FMA=1024 不变，每链轮数分别 1024/256/128。再执行：

```bash
ncu --section LaunchStats --section SpeedOfLight \
    --section Occupancy \
    --kernel-name-base function -k 'regex:.*fma.*' -s 10 -c 1 \
    --replay-mode kernel --cache-control all --clock-control base \
    -o log/fma_c1.ncu-rep ./build/lesson03
ncu --import log/fma_c1.ncu-rep --page details
```

4/8 链分别改报告名 `fma_c4.ncu-rep`、`fma_c8.ncu-rep`；`regex:` 表示正则表达式匹配，`.*fma.*` 中两侧 `.*` 允许任意字符，因此选择名字含 fma 的函数，必须核对实际只有目标 `fma_chain` 被采集。

**预测与替代解释：** 多条链可能增加寄存器需求，但不保证寄存器增加、理论占用率下降或时间缩短。固定 FMA 总数不代表总机器指令数完全相同：外层循环轮数减少、末尾求和增加。**Spill（寄存器溢出）**指部分值改放在线程私有的 Local Memory 地址空间，这通常走设备内存与缓存路径，不是额外的片上寄存器；不能凭数组 `acc[Chains]` 的写法断言发生了 Spill。需要时把 `-Xptxas=-v` 加到步骤 2 的 nvcc 命令中，令目标代码生成阶段打印资源与溢出信息，并显式重编；指令依赖与动态性能证据留待后课。

程序还打印 `logical_FMA_FLOPs=2*N*1024`：按常用约定一次 FMA 算一次乘法加一次加法，即 2 FLOP（浮点操作），这里只统计 FMA 部分，不含每线程最后 `chains-1` 次加法。`GFLOP/s` 的分子为这些操作数，分母为普通 Event 平均秒数再乘 `10^9`，表示每秒十亿次操作；若时间用 ms，等价于 `FLOPs/(ms*10^6)`。这是所注明工作口径的派生速率，不是占用率，也不是本次实测。

**异常检查：** total 必须为正且能被 chains 整除；改 chains 后输出配置不变先查重编。若时间为零或非常短，检查规模和计时分辨率，不计算无穷吞吐。

## 6. 总结与验收：把资源上限与时间分开

A、D 分表记录配置、grid、寄存器、静态/动态共享内存、理论占用率、限制资源、普通运行时间范围与 NCU Duration，未测字段写“未测量”。**Duration** 是 NCU 采集对象的时长；普通 Event 时间来自不启动 NCU 的基准测试，两者分列，不能混为一次测量。


独立回答：

1. 128 与 256 的理论占用率相同，时间不同，是否矛盾？不矛盾，上限不描述全部执行行为。
2. 寄存器总量够用，为什么工具仍可能少算一个块？还要核对分配粒度、分区、共享内存、线程与块槽位等其他约束。
3. 多链理论占用率下降，能否断言结果错或必然更慢？不能；先各自核对输出，再核对编译资源，时间原因留待执行证据检验。

**第四课接续，不属于本课验收：** Achieved Occupancy 是动态平均活跃 Warp 比例，不能拿来替代这里的理论预算；短执行、块不足或尾部部分 SM 已空闲都可能影响它，口径与推导见 [lec04 第 1 节](../04_warp_scheduling/lec04.md)。进一步采集可在本课配置基础上增加 `--section SchedulerStats`（调度统计组），但须先学习第四课：Active 表示驻留且未结束，Eligible 表示下一条指令已满足发射条件，Issue 是将指令送去执行；Active 多不表示 Eligible 多。多链的独立指令工作叫 ILP，多个 Warp 提供工作叫 TLP（线程级并行），两者与循环指令变化的权衡在第四课第 9 节分析。本课只保留这些后续问题，不据此诊断调度瓶颈。
