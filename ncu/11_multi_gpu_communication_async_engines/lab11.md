# 实验 11｜同一个 GPU1 kernel，换一个输入所在的设备

## 背景：直接读另一张卡，省掉的是什么？

先建立本实验的执行模型：CUDA 是 GPU 编程与运行平台，**kernel** 是在 GPU 上由许多线程执行的函数，**launch** 是 CPU 提交一次函数调用；host 是在 CPU 上准备数据和调用 CUDA 的部分，device 是 GPU。这里 **copy kernel** 指线程逐项读写的复制函数，不是专用复制硬件任务。

假设 GPU0 已有一份数组，GPU1 想使用它。一种思路是先复制成本地数组，另一种是允许 GPU1 的线程直接访问 GPU0 的地址。本课只隔离后一种访问行为：GPU1 执行同一个 copy kernel，分别读本地输入与远端输入。**不计输入准备成本，也不比较两套端到端搬运方案。** 这是需要两张可见 GPU 的独立选修。

配合 [lec11](lec11.md) 第 2–4 节读延迟/带宽模型、SM-P2P 与观测边界。P2P（peer-to-peer）是设备间直接访问能力；**指针**是某块内存的地址，不携带“替你搬运数据”的行为；`cudaSetDevice` 选择当前 CPU 线程后续 CUDA 操作的设备，不迁移已经分配的数据。SM 是执行普通 GPU 线程的计算单元，CE 是专用复制引擎，二者不是一回事。

被测的 `copy_kernel` 接收一个输入指针 input、一个输出指针 output 和元素数 n，做的事只有 `output[i]=input[i]`。例如输入 `[0,1,2,3]`，输出也必须是 `[0,1,2,3]`；这不是向量乘，更没有求和。线程 i 从输入第 i 个 float 取值，写入输出第 i 个位置，线程之间不交换数据。输入指向远端时，变化的是这次 load 需要访问哪张卡的存储，而不是线程计算公式。

float 是每元素 4 字节的单精度浮点格式；load/store 分别是读/写。GPU 线程以 **block（线程块，也叫 CTA）**分组，本次启动的所有块构成 **grid**，例如 256 线程一块，16 个元素仍会启动一块，但只有前 16 个线程读写。

host 在 GPU0 建立 source0，在 GPU1 建立内容相同的 local1，并在 GPU1 分配 output1。两份输入都上传且等待准备完成后，host 始终在 GPU1 提交 kernel，只把 input 参数选择为 source0 或 local1；最后等待、下载 output1，与 CPU 原始输入逐项比较。先拿相同内容填两份输入，是为了让 local/peer 对照只有地址归属不同，不把数据值变化混进来。小输入默认 n=16，所以线程 0–15 各复制一个数；启动出来的其他线程不读也不写。

这个选择把通信问题缩到一条容易核对的数据路径：GPU1 的线程读、GPU1 的线程写。若远端版发生变化，先考虑读取路径，而不是浮点计算量或输出位置变化。不过“两个版本都正确”只能验证这份稳定输入的复制，不能证明互连饱和；“远端更慢”也要等规模、计时范围和缓存条件明确后才能解释。接下来的顺序因此是先画地址归属，再确认访问权限与源数据就绪，最后才比较时间与指标。

源码只读本课 [main.cu](kernels/main.cu) 与共享 [common.cuh](../kernels/common.cuh)。按 `copy_kernel → main 常量 → 能力检查 → 分配上传 → time_kernel → 核对释放` 顺序读。以下命令为未来操作，统一在 Linux/Bash 的 `cuda/ncu/11_multi_gpu_communication_async_engines/` 执行。

## 1. 先画设备、数组与线程的对应关系

**目的与代码：** 默认 n=16、block=256、warmup=10、repeats=20，`use_peer=true`。先纸上分析，不执行命令。

**Event（CUDA 事件）**是在某条 GPU 提交队列上记录的完成点，计时事件还可提供时间戳；队列叫 **stream（流）**，其中提交的工作受顺序约束，不同流/设备之间不自动等待。例如 GPU1 的 start→copy→stop 在同一流中，等 stop 后才可读计时间隔，不能因输入指向 GPU0 就把它理解为 GPU0 的计时。

| 对象 | 所属设备 | 本地模式 false | peer 模式 true |
| --- | --- | --- | --- |
| source0 | GPU0 | 已初始化但不读 | 被 GPU1 读取 |
| local1 | GPU1 | 被 GPU1 读取 | 已初始化但不读 |
| output1 | GPU1 | GPU1 写入 | GPU1 写入 |
| kernel、计时 Event | GPU1 | 相同 | 相同 |

两份输入都由 CPU 按 `input[i]=i%251` 初始化，N=16 时预期复制出 `0,1,…,15`。`%` 是整数取余；`i=blockIdx.x*blockDim.x+threadIdx.x` 中三项分别是块号、每块线程数、块内线程号，例如块 1 的线程 0 在每块 256 线程时负责 i=256；当前只有一个 block，线程 0–15 有效，其余由 `i<n` 排除。没有浮点算术，所以可逐项精确比较全部 N 个输出。

```text
local：GPU1 local1 ──GPU1 线程读取──→ GPU1 output1
peer ：GPU0 source0 ──受支持的互连访问──→ GPU1 线程 ──→ GPU1 output1
```

**解释与检查：** 唯一被测变化是输入位置，kernel 和输出位置没变。初始化同时准备两份输入，均在计时外；不能把这些上传也算进打印的 kernel 时间。若把 peer 理解成 GPU0 执行 copy，回看计时前最后一次 `cudaSetDevice(1)`。

**理解检查：** 一个指针指向 GPU0，为何不能仅凭它推断 kernel 在 GPU0 执行？

## 2. 推导访问方向与初始化顺序

**同步**要回答谁在等待、等哪项工作、何时能安全使用数据。例如 CPU 等待 GPU0 上传完成后才去提交 GPU1 读取，建立了“先上传、后读取”的顺序；P2P 权限只解决可访问地址，不建立这种顺序。API 是可调用的程序接口，下文每个 `cuda...` 函数都是一个 CUDA API。

设备图只描述我们希望发生什么，尚未保证硬件允许这样访问。指针值有效不等于 GPU1 已获准读取它；即使允许访问，也不等于 GPU0 的上传已经完成。这是两个不同前提：能力/开启解决“能否访问”，初始化后的等待解决“开始读时数据是否就绪”。本例源端测量期间不再修改数据，因而可以用一次先完成后读取的顺序建立稳定输入，无需引入复杂的跨卡生产者—消费者协议。

**目的与代码：** 阅读能力查询和同步，不运行命令。将每次调用翻译成一句话：

1. `cudaGetDeviceCount` 检查至少两张可见设备；无设备或不足两张时返回 `SKIPPED`、退出 77，不是 PASS。其他 CUDA 错误直接报告。
2. `cudaDeviceCanAccessPeer(&can_access,1,0)` 问“GPU1 能否访问 GPU0 的内存”。方向不支持也跳过；本地模式跳过 P2P 查询，但仍要求两张 GPU。
3. 切到 GPU1，再调用 `cudaDeviceEnablePeerAccess(0,0)`：第一个 0 是 peer GPU0，第二个 0 是当前要求的 flags 值。它只开启 GPU1→GPU0 访问，不自动开启反向。
4. 切到 GPU0 分配/上传 source0，并同步；再切到 GPU1 分配/上传 local1，并同步。GPU0 此后不修改源数组，GPU1 读到的是已准备好的稳定输入。
5. GPU1 执行并同步完成，下载核对后在 GPU1 释放本地数组、关闭 peer；最后切回 GPU0 释放 source0。

**预期与解释：** 这里不需要另造跨卡轮询协议，因为源端先完成初始化、测量阶段不再写。不能把这个顺序推广成“跨 GPU 任意读写都自动同步”。

**异常检查：** 设备编号是进程可见逻辑编号，未核对映射前不等于固定插槽；**context（上下文）**是进程在某设备上的 CUDA 状态与资源容器；当前设备选择决定后续操作针对哪张卡，不是迁移指针指向的存储。查询方向反了、当前设备/上下文不对或先读后初始化，都会破坏本实验的前提。不要通过关闭错误检查把失败伪装成成功。

## 3. 先做小输入本地正确性，再测 peer 正确性

**目的与命令：** 未来先确认设备、驱动、Toolkit 和分析器。以下仅查询环境，不代表已核实 P2P：

```bash
nvidia-smi
nvidia-smi topo -m
nvcc --version
ncu --version
ncu --list-sections
```

`nvidia-smi` 查 GPU/驱动，驱动负责系统与设备交互；`nvcc --version` 查 CUDA 编译器版本，Toolkit 是包含该编译器和头文件等的开发工具集合。**NCU（Nsight Compute）**是 kernel 性能分析器，`--version` 查版本，`--list-sections` 查可用 section（按问题组织的指标组）。**拓扑**是设备间连接方式；`topo -m` 查看物理拓扑矩阵，不能替代程序的方向能力查询。compute capability 是设备指令能力编号，也需按两张实际 GPU 确认。下面 `sm_89` 是示例，必须选择执行 GPU 及工具链支持的架构。

先只把源码 `use_peer` 改为 false，保留 n=16 等常量：

```bash
mkdir -p build log
nvcc -std=c++17 -O3 -lineinfo -arch=sm_89 kernels/main.cu -o build/lesson11
```

`mkdir -p` 创建缺失目录；`-std=c++17` 指语言标准，`-O3` 优化，`-lineinfo` 保留源码行映射，`-arch` 选择目标 GPU，`-o` 指产物。没有 CLI（用于运行时选择模式/规模的命令行参数），改源码/共享头后都须显式重编。

之后独立运行：

```bash

```

**看什么：** 先确认 `mode=local n=16 block=256`，再看 `checked=16 errors=0`、PASS 和退出 0。只将 use_peer 改回 true，重编、再单独运行；peer 同样必须全量核对，或如实 SKIPPED/77。表中输出是验收预期，不是本次实测。

**异常检查：** 按首个 CUDA 错误 → 可见设备数 → 方向 `(1,0)` → 是否重编排查。SKIPPED 没有性能样本；不自动改驱动、容器、权限或 GPU 设置。编译失败不可拿旧产物继续当成新版本。

**边界练习：** 固定一种模式，把 n 单独改为 257，重编运行；应有两个 block，第二块只有 1 个有效线程，必须 checked=257。通过后再在另一模式重复同一边界检查。

## 4. 理解 avg_ms 的分子与分母

小输入 PASS 后，已知的是访问与索引在该配置下正确，还不知道耗时主要来自哪里。16 个 float 的有效载荷只有 64 字节，即使远端每字节服务更贵，固定启动成本也可能掩盖差别。因此先弄清 avg_ms 的计时窗口，再增加 N；不能把小输入两个相近的数当成链路带宽结论。增加 N 是建立新的性能基线，不与旧 N 算加速比；之后固定 N 切换输入地址，才是访问位置的对照。

**目的与代码：** 读共享 `time_kernel`：10 次预热后同步；GPU1 上创建并记录 start Event，提交 20 次 kernel，记录 stop，等待 stop，再取毫秒数除以 20。本例使用的计时 Event 提供设备时间轴上的时间戳；CPU 等待 stop，才保证这批工作完成。

步骤 3 的普通运行输出 `avg_ms`，其范围只包括这批 GPU 启动，可能含 CPU 提交不及时的间隙。分配、host 上传、peer 开启、下载和 CPU 核对均不在其中。**批量平均**是这一次 start 到 stop 的总毫秒数除以启动次数 20；单次分布是分别测每次调用再看快慢差异，两者不同。**墙钟时间**是现实中从约定程序起点到终点经过的全部时间，包含窗口外准备等成本。它既不是单次分布，也不是程序总墙钟时间。

`1<<24` 是左移，等于 2²⁴=16,777,216；1 MiB=2²⁰ B。多次运行所得批量均值可排序取中位数（中间值），离散程度可用最大/最小差或分位区间描述，要保存各次原值，不把一批中的 20 次当作 20 个独立计时样本。

**单变量实验：** 正确性通过后，先单独将 n 设为 `1<<24` 建立大输入配置，再固定 N、block=256、编译参数、GPU 对及方向、预热/重复，只切 use_peer=false/true。GPU0 源约 64 MiB，GPU1 两数组约 128 MiB；先检查设备及 host 内存，不保证该工作集超过实际缓存。每版显式编译，多次普通运行并记录批量均值的中位数与离散程度，不能把单个均值当成统计可信度。

**模型推导：** N 是元素数，每项 4 B。若普通运行 `avg_ms` 为毫秒，则 `t=avg_ms/1000` 秒；`4N/t` 的分子是 N 项输出承载的有效数据字节，得到 B/s；除以 10⁹ 可写成 GB/s。`8N/t` 则是逻辑读取 4N B 加写入 4N B 的合计速率。GPU1 的本地输出写入不应算作跨卡载荷。两种口径都不是实测链路字节数。小 N 时固定启动成本可能占主导，大 N 时才更有机会观察传输特征，但不保证 peer 必然更慢。

**异常检查与练习：** 若两模式时间接近，先查 N、模式、环境竞争、缓存和波动，不立即宣布“互连与本地等速”。固定大 N/模式后可再单独改 block 为 128；或单独改 repeats 为 100，后者也可能改变缓存热度，不代表冷传输性能。

## 5. NCU 只先回答 GPU1 kernel 的问题

普通 Event 时间只能说明这一批 GPU1 kernel 用了多久，并不能单独说明时间花在远端等待、本地写出还是其他资源上。NCU 的用途是给这个 GPU1 kernel 增加资源与访存线索，而不是把 copy 改成专用复制引擎的任务。由于 local 与 peer 保持相同线程索引和本地输出，先检查启动与资源相同，再找读取侧的差异，才与实验假设对应；若报告看见的不是 GPU1 上的目标启动，后续解释就失去对象。

**目的与命令：** 普通运行通过后，确认本机选项/Section 支持，从本课目录采首个正式启动。先以 local 配置生成报告，peer 重编后把报告名改为 `copy-peer`：

```bash
mkdir -p log
ncu --set basic -k 'regex:copy_kernel' -s 10 -c 1 \
  -o log/copy-local ./build/lesson11
```

`--set basic` 是基础指标组，`-k` 按正则筛函数，`-s 10` 跳过匹配的 10 次预热，`-c 1` 只采其后一次，`-o` 指报告前缀。这里没有第 10 课的命名范围，所以不能省略 skip 的原理分析。已存在同名报告时手工改名，不强制覆盖。

NCU 可能为分轮采不同指标而 **replay（重放）**目标调用，一轮叫 pass；也可能把原先重叠任务改为依次执行（串行化）。这与程序自己做 20 次计时启动不同，不能把采集中的时间当作普通基准。

**看什么与解释：** 先核对 GPU1、函数、grid/block、运行配置；basic 概览看 LaunchStats（启动形状与资源）、SpeedOfLight（相对所用峰值定义的吞吐概览）；后者不是“有效工作时间占比”。需要解释访存时，另一次针对性添加 `--section MemoryWorkloadAnalysis`，报告另名。记录原始指标名、单位、作用域，再解释资源和延迟；远端访问的 replay 支持及指标归属依设备/版本核对，不预设所有路径都能采。

**异常检查：** 无结果先查 SKIPPED、过滤器及工具原始错误；缺少远端/链路指标写“未采集/不支持”，不填零。NCU 的重放和串行化可能扰动执行，报告 Duration 与普通运行 avg_ms 分开保存，不能拿采集耗时宣称端到端加速。

## 6. 用反例划清通信结论

**目的：** 对照 [lec11](lec11.md) 第 3、4、11 节，把“知道”与“不知道”分开。纸上逐项作答，不需要新命令。

为读懂下面的反例：**NVLink** 是某些 GPU 间的高速互连，**PCIe** 是另一种常见设备总线，支持 P2P 不自动证明使用哪一种。**NSYS（Nsight Systems）**记录 CPU/API/GPU 活动时间线，显示何时复制/执行/等待，但时间线本身未必逐字节标出物理路线。**NIC** 是网卡，**RDMA** 是网卡在权限和注册规则下访问远端内存的机制；它不等于 GPU 线程在网络上逐字节搬运。

| 已有证据 | 能说明 | 不能说明 |
| --- | --- | --- |
| `(1,0)` 能力为真 | 该方向允许 peer access | 一定走 NVLink |
| peer 模式 PASS | 当前输入的全部结果正确 | 链路饱和或协议普遍正确 |
| GPU1 copy kernel 指标 | SM 发起的访问及相关资源线索 | CE、NIC 或整个互连的完整性能 |
| 拓扑矩阵、NSYS 时间线 | 设备连接条件及执行/同步活动 | 每个字节实际走哪条物理链路 |

TMA（Tensor Memory Accelerator）是特定架构的批量/多维异步搬运机制，常用于 global 与同块 shared memory（块内共享存储）之间，不是通用跨卡复制引擎。NCCL 是 GPU 集体通信库（如多方求和后各得结果），NVSHMEM 提供按其规则访问对端数据与同步的通信接口；“通信计算重叠”指它们的执行时间区间有交集，而非简单说“调用了 Async API”。这些只用于划清本 lab 未覆盖的边界。

`cudaMemcpyPeerAsync` 是向 CUDA 提交设备间异步复制的 API，不等于启动本例的线程复制函数，也不能仅凭接口名字证明必定使用 CE。这仍是 SM 的普通 load/store kernel，并未测量该 API；也没有以 CE、TMA 为被测对象，未实现 NCCL、NVSHMEM、NIC/RDMA 通信或通信计算重叠。链路归因需要适用的传输计数器、明确窗口与拓扑交叉支持，不能把 GPU1 的 DRAM 字节当 NVLink 字节。

**完成检查：** 画出 peer 数据路径；解释查询 `(1,0)`、只开启一个方向、输出始终在 GPU1 和源端先同步的原因；写出一种能够推翻“跨卡一定慢”的观测，并说明还须排除哪些因素。

## 7. 动作入口与已有证据边界

理解底层命令后，在本课目录分别执行：

```bash
CUDA_ARCH=sm_89 bash commands/compile.sh
bash commands/run.sh
bash commands/profile.sh
```

三个脚本均无位置参数、按自身位置定位；仅 compile 必填 `CUDA_ARCH`（按设备替换），固定 C++17、`-O3 -lineinfo`，生成 `build/lesson11`，编译前移除旧目标，失败即停止。run/profile 缺产物报错，不隐式构建，改常量/共享头后须重编。profile **先普通执行一次本程序**，作为能力与正确性预检；返回 77 时立即以 77 结束，不启动 NCU，避免 NCU 把应用的跳过转成其他退出码。该预检不是独立计时基线，仍须单独 run。预检通过后，profile 用 basic、copy_kernel 函数基名、skip 10/count 1，固定 kernel replay/cache all/clock base。

新日志为 `log/compile.log`、`log/run.log`、`log/profile.log`，含展开命令、输出与 `exit_code`；重跑覆盖各自新日志，对照需先另存。报告 `log/profile.ncu-rep` 已存在则拒绝覆盖，NCU 失败即停止，报告内容由实验者检查。`77/SKIPPED` 是未执行采集，不是 PASS。
