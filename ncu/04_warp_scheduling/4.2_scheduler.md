# 4.2 NCU Scheduler Statistics：Theoretical、Active、Eligible 与 Issued Warp

配套讲义：[第四课：实际驻留、Warp 调度、依赖与 Stall 分析](lec04.md)。先通过 [4.1 Tail Effect（尾部效应）](4.1_tail.md) 区分理论容量与实际驻留，再在本文分析已经驻留的 Warp 为什么能够或不能发射指令。静态资源预算见[第三课](../03_occupancy/lec03.md)。

> 主题：理解 NVIDIA GPU 的 SMSP / Warp Scheduler 如何管理驻留 Warp、判断指令就绪并完成发射。适用于 Nsight Compute（NCU）的 Scheduler Statistics 学习。

## 1. 核心结论

先回顾执行单位：**kernel** 是 GPU 上许多线程执行的函数，线程组成 **Block（线程块，也叫 CTA）**，本次全部块组成 **Grid**。GPU 上的 **SM** 是接收并执行块的硬件单元，块内每 32 个线程组成一个 **Warp**。Warp 被分配执行状态和资源、尚未完成时称为**驻留**，即使它在等待也没有离开硬件。

**Warp Scheduler（Warp 调度器）**负责在驻留 Warp 中选择下一条指令，把它交给执行路径，这一步叫 **Issue（发射）**，不是“结果已经算完”。调度器并不是让一个 Warp 连续执行完全部指令后才调度其他 Warp，而是不断从自己管理的驻留 Warp 中选择下一条指令已经准备好的 Warp 发射。由此需要区分四个层次：**理论容量（Theoretical）→ 实际驻留（Active）→ 当前可发射（Eligible）→ 本周期真正发射（Issued）**。它们并非四个互斥状态：Issued Warp 属于 Eligible Warp，Eligible Warp 属于 Active Warp，而 Theoretical Warps 是容量上限。周期是硬件时钟的一拍；Issue Active 统计有发射活动的周期比例，例如观察 8 周期，6 周期发射则为 75%，不代表单条指令已完成。

表中寄存器是保存线程中间值的片上存储，Shared Memory 是同一块线程共用的片上数组空间，Block Size 是每块线程数。这些资源有限，决定能放多少 Warp。SMSP 是 SM 的子分区，下节会用它说明调度器的管理范围。

| 概念 | 具体含义 | 是否一定正在执行指令？ |
| --- | --- | --- |
| **Theoretical Warps** | 当前 Kernel 的寄存器、Shared Memory、Block Size 等资源约束下，每个 Scheduler 理论最多可驻留的 Warp 数 | 否，仅表示容量 |
| **Active Warps** | 已经分配到 SMSP、尚未完成的驻留 Warp | 否，可能长期等待 |
| **Eligible Warps** | 当前下一条指令已满足依赖和发射条件的 Warp | 否，可能未被选中 |
| **Issued Warp / Issue Active** | 实际被调度器选中发射指令的 Warp；Issue Active 表示存在发射活动的周期比例 | 是，指令已经发射，但不代表该指令已完成 |

## 2. SMSP 与 Warp Scheduler 的硬件关系

以典型的四 SMSP NVIDIA SM 为例，一个 SM 分成四个 SM Sub-Partition（SMSP，SM 子分区），每个 SMSP 拥有自己的 Warp Scheduler、寄存器资源及部分执行管线。**管线**像可重叠工作的加工步骤：一条指令尚未做完，后面的独立指令也可能已进入处理，不等于一次只能做完一条。某个 CTA 被安排到 SM 后，其 Warp 被分配到相应 SMSP；一个 Warp 驻留期间由所属 SMSP 的调度器管理。L1 Cache 和 Shared Memory 等资源通常在 SM 层面共享，具体组织因架构而异。

假设 SMSP 0 根据资源限制最多驻留 8 个 Warp，当前真实驻留 6 个，即 **Theoretical = 8、Active = 6**。Active 的意思接近 *resident*（驻留），不是每周期都在 *running*（执行）。一个 Warp 即使等待 Global Memory Load 数百个周期，仍然是 Active。

## 3. 单周期实例：六个驻留 Warp

**周期（Cycle）**是硬件时钟推进的一拍，不是固定多少纳秒；下表只用它标记调度时刻。FP32 是 32 位浮点数（如 `float`），ADD 是加法，Load 是读取，Global Memory 是设备全局地址空间。**Barrier（会合屏障）**要求参与线程到齐后再继续，例如 `__syncthreads()` 让同块线程等待彼此完成前一阶段。

某个周期有六个 Active Warp：

| Warp | 下一条指令或等待原因 | 本周期是否 Eligible？ |
| --- | --- | --- |
| W0 | 下一条 FP32 指令已准备好 | 是 |
| W1 | 等待 Global Memory Load 数据返回 | 否 |
| W2 | 下一条整数 ADD 指令已准备好 | 是 |
| W3 | 等待前一条计算指令产生结果 | 否 |
| W4 | 等待 CTA Barrier | 否 |
| W5 | 下一条 Load 指令已准备好 | 是 |

因此，**8 Theoretical → 6 Active → 3 Eligible → 1 Issued**（这里假设调度器本周期只选择一个 Warp 发射）。如果调度器选中 W2，那么 W0 和 W5 虽然 Eligible，却因未被选中而处于 **Not Selected**。这通常不是错误或真正的执行停顿，而是发射资源有限时的自然结果。不同架构的指令发射宽度和管线共享方式可能不同，不能将“每周期一个 Warp”推广为所有硬件的绝对规则。

## 4. 为什么 Active 不一定 Eligible？

考虑简化 CUDA Kernel。指针 `in`、`out` 表示数组起始位置，`in[i]` 是第 i 个元素，`const` 表示不通过该指针修改输入；`__global__` 标记 GPU 函数。`blockIdx.x` 是块号，`blockDim.x` 是每块线程数，`threadIdx.x` 是块内线程号，例如第 2 块的第 3 个线程、每块 256 线程时，`i=2*256+3=515`。例子省略边界检查，仅假定数组足够大、启动大小正好覆盖输入，不应直接用于任意 N：

```cpp
__global__ void scale(float* out, const float* in) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    float x = in[i];
    float y = x * 2.0f;
    out[i] = y;
}
```

`float` 是 4 字节浮点数，`2.0f` 的 `f` 表示单精度常量。相关操作可以抽象成 `LDG → FMUL → STG`，分别是全局读取、浮点乘法、全局写入；这些是机器指令名称的示意，实际生成形式要看编译结果。假设 W0 已发射 `LDG`，而 `FMUL` 依赖尚未返回的寄存器值，那么 W0 虽然仍然驻留，却不能发射这条 `FMUL`，暂时不 Eligible。调度器此时可以选择 W1、W2 等其他已就绪 Warp 执行指令。这就是 GPU 使用多个驻留 Warp 隐藏延迟的基本机制：不同 Warp 的上下文（下一条指令位置和各线程的中间值等）已存放在硬件中，通常不需每次换 Warp 都把整套状态存到别处再恢复。

先解释下表按什么机制分类。**Scoreboard** 是跟踪未完成操作及其依赖的硬件机制，像在“R4 的新值还没回来”旁做标记，避免后面的计算读到旧值。**L1TEX** 是处理全局、线程私有 Local、纹理等访问的硬件路径；纹理访问是一类带专门寻址/取样功能的读取。**MIO（Memory Input/Output）**是另一类指令的输入输出处理路径，常涉及 Shared Memory，也涉及部分特殊操作；它不是 DRAM 的别名。Long/Short Scoreboard 按依赖所属路径分类，不是按统一周期阈值分“长短”。

**Throttle** 指入口或管线暂时不能接收新指令，像队列已满；它与“先前已发出的操作结果未回”不同。**前端取指**是取来并准备下一条机器指令。NCU 的 **Stall Reason** 是 Warp 下一条指令无法发射的原因，而不是整个 GPU 停工的原因。常见不可发射原因包括：

| 类别 | 典型原因 | NCU 可能观察到的 Warp Stall Reason |
| --- | --- | --- |
| L1TEX 路径的数据依赖 | Global/Local/Texture 等数据加载尚未完成 | Long Scoreboard |
| MIO 路径的数据依赖 | Shared Memory 或部分特殊操作尚未完成 | Short Scoreboard |
| 计算依赖 | 连续依赖的算术指令 | Wait / Dependency 相关状态，依架构而定 |
| 同步等待 | `__syncthreads()` 等 CTA 同步 | Barrier |
| 管线或资源限制 | 目标管线、指令队列暂不能接受操作 | Math Pipe Throttle、MIO Throttle 等 |
| 指令未准备好 | 指令获取或前端供给问题 | No Instructions 等 |

上述映射是典型情况，不是严格一一对应；具体 Stall Reasons 应以所用 GPU 架构和 NCU 版本的官方定义为准。

## 5. 为什么 Eligible 不一定 Issued？

调度器可能同时看到多个 Eligible Warp，但其每周期发射能力有限。假设 W0、W2 和 W5 均已就绪，而本周期只允许选择一个 Warp，调度器选择 W2 后，其余两个就是 Not Selected。**Eligible 多表示可供调度的候选工作多，并不表示这些 Warp 必须同时发射。**

相比“Not Selected 较高”，更需要警惕的是调度器经常一个 Eligible Warp 都没有：这种情况下即使有很多 Active Warp，发射槽位也可能空闲，Issue Active 会偏低。

## 6. 跨周期实例：平均值如何形成？

假设 SMSP 的理论容量始终为 8，实际驻留始终为 6；观察连续 8 个周期，并假设每周期最多发射一个 Warp：

| Cycle | Theoretical | Active | Eligible | Issued |
| --- | ---: | ---: | ---: | ---: |
| 0 | 8 | 6 | 3 | 1 |
| 1 | 8 | 6 | 2 | 1 |
| 2 | 8 | 6 | 1 | 1 |
| 3 | 8 | 6 | 0 | 0 |
| 4 | 8 | 6 | 0 | 0 |
| 5 | 8 | 6 | 2 | 1 |
| 6 | 8 | 6 | 3 | 1 |
| 7 | 8 | 6 | 1 | 1 |

由此得到：

\[
\overline{W}_{theoretical}=8,\quad
\overline{W}_{active}=6,\quad
\overline{W}_{eligible}=\frac{12}{8}=1.5
\]

\[
\text{Issue Active}=\frac{6\text{ 个发生指令发射的周期}}{8\text{ 个观察周期}}=75\%
\]

平均 Eligible 的单位是“Warp/调度器/周期”的平均数量，75% 则是周期比例，不能把两个数直接相除解释为硬件效率。

这说明 **Active = 6 并不能保证每周期都发射**：第 3、4 周期仍有六个驻留 Warp，但没有任何 Eligible Warp。注意 Issue Active 是“有发射活动的周期比例”，不等同于所有架构下的 IPC（Instructions Per Cycle，每周期发射或执行的指令数，需注明哪一种）；`Issued Warps / Eligible Warps` 也不是标准的 Issue Active 计算公式。NCU 报告还会按活跃周期、SM/SMSP 等维度聚合，解读具体计数器时需核对其定义。

## 7. 如何用 NCU 诊断？

读表前区分报告组：Occupancy 看驻留比例，Launch Statistics 看启动规模，Warp Stall Reasons 看等待原因，Source Counters 把计数或采样关联到代码位置。部分 **Wave** 指 Grid 工作块数不足以填满一次全 GPU 驻留容量，例如容量 52 块而末段只剩 24 块；它不是内存路径的 Wavefront。

| 观察现象 | 初步解释 | 下一步查看 |
| --- | --- | --- |
| Theoretical Warps 低 | 寄存器、Shared Memory、Block Size 或其他资源限制 | Occupancy、Launch Statistics |
| Active 显著低于 Theoretical | Grid 规模不足、部分 Wave、CTA 负载不均衡等 | `launch__waves_per_multiprocessor`、执行时间分布 |
| Active 高而 Eligible 低 | 已驻留 Warp 因依赖、同步或资源等待无法发射 | Warp Stall Reasons、Source Counters |
| Eligible 低且 Issue Active 低 | 调度器经常缺少可发射的工作 | Long/Short Scoreboard、Barrier、依赖链 |
| Eligible 高且 Issue Active 高 | 调度器通常有充足候选 Warp 且持续发射 | 管线吞吐、指令效率与实际 Kernel Duration |
| Not Selected 高且 Issue Active 高 | 就绪 Warp 多于当前发射容量 | 不必单纯追求降低 Not Selected |

要分清两种不同的性能瓶颈：**第一，为什么没有更多 Active Warp？** 应检查 Grid 大小、CTA 分配、Tail Effect 和资源驻留上限；**第二，为什么 Active Warp 无法提供更多 Eligible Warp？** 应检查数据依赖、Scoreboard、同步和管线资源。前者是并行工作供应或驻留问题，后者是已驻留工作能否推进的问题。

这也解释了为什么 **Achieved Occupancy 高不代表 Issue Active 一定高**，而 Issue Active 高也不自动等于指令执行吞吐或 Kernel 性能最优。真正的性能判断仍应结合 Duration（实际执行时间）、SOL（Speed of Light，NCU 中相对于硬件参考峰值的吞吐概览，不是“时间占比”）和执行管线指标。

## 8. 与 Tail Effect 的联系

Tail Effect 属于 CTA/Grid 层面的并行度不足。如果最后一波只有少量 CTA，部分 SM 将没有新的 CTA 可以驻留，从而减少全设备的驻留工作；但 NCU 的 Occupancy 是否以及下降多少，还取决于活动周期归一化和各 SM/SMSP 实例的聚合，不能用空闲 SM 比例直接换算；这和一个已驻留 Warp 因 Load 依赖而 Stall 是两种不同机制。可沿着 **Grid/CTA → SM/SMSP 驻留 → Active → Eligible → Issued → 执行管线吞吐** 的顺序定位问题。

已经分清四个层次后，可继续读 [4.3 Warp Stall](4.3_stall.md)，从“结果未回、入口拥堵、参与者未到”追查无法发射的机制。
