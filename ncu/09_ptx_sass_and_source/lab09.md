# 实验 09｜从一条乘加依赖链走到真实机器指令

## 要解决的问题

假设你反复计算 `a=a*m+b`。下一次乘法必须先拿到上一次的 a，线程再多也不能消除**同一线程内部**的这条依赖。若同时维护四个互不依赖的 a，编译器是否能穿插它们？代价又是什么？本课不是背 SASS 助记符，而是练习“源码预测 → 静态指令核对 → 运行核对 → 指标支持或反驳”的证据链。

可配读 [lec09 第 1–2 节](lec09.md)、第 4–7 节：分别解释编译层次、采样归因和寄存器压力；下面会在每步补齐所需知识，不要求先读完讲义。讲义中的 SASS 是示意，不能当作本程序反汇编结果。

先看执行分工：**kernel** 是 GPU 上运行的函数，**线程**是执行它的一份工作实例；线程按 **block（线程块）**协作，全部块组成启动的 **grid**。硬件按每 32 个线程组成 **warp**，组内位置叫 lane。GPU 的 **SM** 是容纳并执行这些线程的处理单元。**寄存器**是线程保存当前数值与地址的快速小存储；producer 指令产生一个值，consumer 指令使用它。PTX 是虚拟指令表示，SASS 是具体 GPU 的机器指令的可读形式。例如源码 `a=a*m+b` 可能生成一条融合乘加指令，不能按源码运算符个数推断机器指令数。

**FMA（融合乘加）**计算 `a*m+b`，只做一次最终舍入，本例 `fmaf` 操作的是 32 位 `float`（FP32，4 字节）。一次 FMA 按一乘一加计 2 **FLOPs（浮点运算次数）**；FLOP/s 才是每秒多少次。**ILP（指令级并行）**指同一线程内存在可以独立推进的指令，不代表新增 CUDA 线程。

本课的 `fma_chain` 不是把两份数组相乘，而是让每个有效线程自己生成初值，反复乘以 1.0001 再加 0.0001，最后只输出一个 float。以线程 0 的单链为例，初值 0.50390625，一轮后约为 0.50405664；下一轮必须使用这个新值。线程 1 从略不同的初值开始，和线程 0 没有数据交换。CPU 代码一侧叫**主机（Host）**，GPU 一侧叫**设备（Device）**。本例总共要计算 N 个输出；kernel 输入包含输出数组地址、输出长度 N、每线程总 FMA 次数和乘数/加数，链数在编译时确定；输出是 N 个结果。主机按 `ceil(N/block)` 个块、每块 block 个线程启动，ceil 表示向上取整，例如 N=2、block=256 仍启动一块，只有两个线程有效。主机只需分配 GPU 输出数组、提交 kernel，再下载结果并用 CPU 重算；这里没有待上传的输入数组。这种几乎只在局部累加值上计算、末尾才写一次结果的设计，使我们容易把注意力放在线程内部的依赖，而不是大量输入搬运。

接下来先缩小到两个有效线程看清递推，再把规模放大；同一组性能对照固定线程数和每线程 FMA 总次数，只改变独立链数。若独立链增多后机器指令确实能够交错、普通运行时间也降低，就支持“依赖限制得到缓解”；若寄存器占用增加或循环控制同时减少，还必须把这些变化纳入解释，不能只看加速比。

读代码的路线是 [main](kernels/main.cu) → [fma.cuh](../kernels/fma.cuh) 的 `fma_initial`、`fma_chain`、`run_fma` → [common.cuh](../kernels/common.cuh) 的 `time_kernel`。下面均以 Linux/Bash、工作目录 `cuda/ncu/09_ptx_sass_and_source/` 为准；命令是后续操作说明，不是本次执行结果。

## 1. 先用两个输出预测依赖，而不是先看耗时

**目的与代码：** `main` 的默认 `example=0` 选择 FMA；把学习配置设为 `n=2`、`block=256`、`chains=1`、`total_fmas_per_thread=8`。这些是源码常量，不是程序参数；每次修改都要重新编译。先只阅读和纸算，不运行命令。

线程编号 `i=blockIdx.x*blockDim.x+threadIdx.x`，即“块号×每块线程数+块内编号”；例如每块 256 线程时块 1 的线程 3 是全局 i=259。只有 i=0、1 有效，其他线程在 `i>=n` 处退出。链 j 的初值是：

```text
acc[j] = 0.5 + i/65536 + (j+1)/256
下一轮 = fmaf(acc[j], 1.0001f, 0.0001f)
```

`fmaf` 是浮点融合乘加，一乘一加后只做一次最终舍入，逻辑上计 2 FLOPs（浮点操作数）。线程 0 第一条链从 `0.50390625` 开始，线程 1 多 `1/65536`。纸上可算第一轮的近似值，但不可把十进制手算近似当成精确 GPU 输出。

```text
chains=1：a0 → FMA → FMA → … → FMA → out[i]    共 8 次
chains=4：a0 → FMA → FMA ─┐
          a1 → FMA → FMA ─┤
          a2 → FMA → FMA ─┼→ 顺序相加 → out[i]
          a3 → FMA → FMA ─┘
```

**预期与解释：** 四条链各做 2 轮，仍是每线程 8 次 FMA，但初始化和末尾加法不同，所以两版输出无需相等。CPU 会按各版自己的递推顺序检查全部 N 项。图是依赖图，不是 GPU 执行时间线。

**先检查什么：** `total % chains` 必须为 0，链数须在 1–64；否则不是合法配置。**循环展开（unroll）**是把多轮循环体复制进机器代码，减少循环判断并暴露独立工作，不是增加本来要算的轮数。若觉得数组 `acc` 必然在显存中，回看内层 `#pragma unroll`：展开后固定下标可能被编译器映射到寄存器，仍要用机器码验证。

**理解检查：** 给四链图加一条跨轮箭头。为什么 a0 的第二轮不能提前于第一轮，而 a1 的第一轮不需要等待 a0？

## 2. 显式编译，再单独验证数值

**目的：** 先证明当前配置能正确计算，再收集性能证据。未来实际执行前，用以下独立命令确认环境：

```bash
nvidia-smi
nvcc --version
ncu --version
ncu --list-sections
```

`ncu` 是 NCU（Nsight Compute，kernel 指标分析器）的命令行入口；Metric 是具体计数项，Section 是一组相关指标。**驱动**让程序使用 GPU，**Toolkit** 是包含编译器等工具的开发包，两者版本不是一回事。`nvidia-smi` 查看可见 GPU 和驱动，compute capability（设备指令能力编号）还需按实际型号/设备查询确认；`nvcc` 是 CUDA 编译器，`--version` 查询版本，`--list-sections` 列出本机支持的 NCU 指标组。下面 `sm_89` 仅是架构示例，按目标 GPU 与 Toolkit 支持范围替换。

```bash
mkdir -p build log
nvcc -std=c++17 -O3 -lineinfo -arch=sm_89 -Xptxas=-v kernels/main.cu -o build/lesson09
```

`mkdir -p` 在目录不存在时创建它；`-std=c++17` 选择语言标准，`-O3` 开优化，`-lineinfo` 保留源码行映射，`-arch` 选择目标架构，`-o` 指输出。`-Xptxas=-v` 把详细资源输出选项交给生成机器码的后端汇编器。不要用默认改变优化行为的 `-G` 调试构建做性能归因；**调试构建**主要服务断点/变量查看，可能改变机器指令，不等于保留优化的性能版本。

先认识寄存器代价：一个值从产生到最后一次可能使用之间都要被保存，这段叫 **live range（活跃区间）**。例如 acc0 尚未用于末尾求和，就不能丢掉它；四条链同时保留四个 acc，可能比单链需要更多寄存器。**寄存器压力**关心某处同时要保存的值及分配约束，**Registers/Thread** 是最终分配数，二者不等同于源码变量个数。

读资源输出前先分清：**栈（stack）**是函数执行中存放部分临时数据/调用状态的区域，不等同寄存器；**spill（寄存器溢出）**是寄存器分配受限时，把某些值暂存出去再读回。**Spill Store/Load** 分别是这种保存/读回，静态资源摘要不等于运行中累计流量。**Local** 是每线程私有地址空间，不代表 SM 上的快速存储，也不是所有函数局部变量都进入它；数组/栈可产生 local 访问，未必是 spill。

**看什么：** 按函数实例记录寄存器、栈、spill loads/stores 等实际输出；没输出的字段不填零。编译失败先读第一条错误，检查头文件与链数；不得用旧二进制继续冒充新配置。

之后另行运行：

```bash
./build/lesson09
```

**预期与解释：** 学习配置应打印 `Chains=1 total/thread=8 rounds=8`、`checked=2` 和 `Check: PASS`。这是验收条件，不是实测。核对要求结果不是 NaN（非数值）或正负无穷，且绝对误差不超过 `1e-5+1e-4*abs(reference)`；reference 是 CPU 参考值，abs 取绝对值，`1e-5/1e-4` 分别是 $10^{-5}/10^{-4}$。失败先看首个 mismatch、实际打印参数和是否重编。

**延迟**是从一次操作发出到结果可用所需时间；**预热**是先执行以减轻首次初始化等影响；**同步**是等待规定的 GPU 工作完成，避免把“提交了”当成“做完了”。`time_kernel` 先预热 10 次，再用 CUDA Event（GPU 时间戳）包住 20 次启动，最后除以 20。分配、下载、CPU 核对在计时外；这个批量均值可能包含主机提交空隙，不是逐次延迟分布。N=2 只用于理解正确性，不能据此推断计算峰值。

## 3. 对同一产物反汇编，找 producer 和 consumer

数值核对只说明递推结果正确，不告诉我们编译器用了哪些指令。源码中的一次 `fmaf`、数组 acc 和循环都可能被展开、重新安排或映射到不同存储位置；因此现在必须换一种证据，检查真正交给 GPU 执行的机器码。先用小配置建立“哪个值由哪条指令产生、下一条指令在哪里使用”的联系，再讨论多链是否提供了独立指令，避免把源码排版当执行顺序。

**目的与命令：** 不改代码，从本课目录检查刚编译的二进制：

```bash
cuobjdump --dump-sass build/lesson09
```

**反汇编**把已编译的二进制显示成人能读的指令，不执行 GPU 工作。**静态代码**描述有哪些指令，**动态次数**描述运行中每条实际执行多少次。`cuobjdump` 是 CUDA 二进制检查工具，`--dump-sass` 输出机器指令。先学一种读法：示意 `FFMA R10,R8,R4,R10` 是新 R10=R8×R4+旧 R10，首个是目的寄存器、后面是输入；下一次使用 R10 就必须等这次产生结果。FFMA 是 FP32 融合乘加的操作名，寄存器号只是示例，不是本程序实测。沿 `fma_chain` 的浮点乘加源/目的寄存器画依赖，区分初始化、循环体、循环分支和最后求和。静态循环体只有几条指令不代表动态只执行几次，必须结合 rounds 和控制流解释。

**对照操作：** 保持 n=2、total=8，只把 chains 改为 4；重新执行步骤 2 的编译、运行，再执行本步命令。预期能寻找多组独立累加值，但不预填寄存器号或指令条数。外层 `#pragma unroll 1` 不要求完全展开，内层展开也不能保证最终 SASS 完全按源码顺序排列。

**异常检查：** 找不到预期 FMA 时先核对函数实例和当前产物，再检查优化是否重排/变形；一行源码可对应多条或多段指令。`-lineinfo` 不保证源码、PTX、SASS 一一对应；当前可执行文件构建命令也不保证报告必有可展示的 PTX。先看 SASS，不为凑三栏伪造 PTX 证据。

## 4. 固定工作量，观察独立链的收益与代价

两个有效线程帮助我们核对每一项递推，却几乎没有提供足够的 GPU 并行工作。即使机器码存在四条独立链，小规模耗时仍可能主要体现启动等固定成本，不能用来衡量这种结构的收益。接下来先扩大工作规模并建立单链基线，然后固定规模只改链数，把“可独立推进”的静态条件转成可被运行时间检验的假设。注意这是增加同一线程内部的独立值，不是增加 CUDA 线程数。

**目的：** 把小例子转成单变量实验。先单独建立 `n=1<<14`、block=256、total=1024、chains=1 的性能基线，再只改 chains 为 4、8；每版执行步骤 2–3，多次普通运行，记录批量均值的中位数及波动。每次程序先报一次整批计时除以启动次数的均值；把多次程序运行所得均值排序取中间值是中位数（偶数个时取中间两项平均），同时保留原始值与最小/最大等范围，不只选最快一次。`1<<14` 是把 1 左移 14 位，即 N=16384。

每版逻辑 FMA 数是 `N*1024`，FLOPs 是 `2*N*1024`，输出都是 N 个 float，即逻辑写入 `4N` 字节。但 rounds 从 1024 变成 256、128，循环控制、初始化与 `Chains-1` 次末尾加法也变了，因此不能声称 SASS 总工作完全相同。

**发射（issue）**是调度器把一条可执行指令交给硬件资源，结果还未必完成。**延迟（latency）**是某条指令发出后多久能使用结果，**吞吐（throughput）**是单位时间完成多少工作；流水线可让独立操作的不同步骤重叠，例如单次需四拍而每拍可送入一条独立运算。**调度器（Scheduler）**挑选下一条满足输入及发射条件的 warp 指令；具备这些条件称 **Eligible（可发射）**。**TLP（线程级并行）**是在一组线程等待时运行其他 warp；**Occupancy** 是 SM 上驻留 warp 数/硬件允许的最大数，驻留指已分配资源且未结束。例如 32/64=50% 不表示算术资源只忙一半。

**预期与反证：** 更多独立链可能隐藏依赖延迟，也可能增加寄存器、降低驻留线程数量；即使加速，循环控制减少也是替代解释。再研究 32、64 链时仍固定 total=1024，不保证一定出现 spill（寄存器值被暂存到其他存储的行为）。若改为 `total=1024*chains`，就是每链固定轮数、总工作增加的另一实验，不能和固定总工作混算加速。

**理解检查：** 四链比单链快，足以断言是 ILP 吗？至少还应核对哪些循环和资源变化？

## 5. 用 Source 把动态现象接回静态依赖

静态指令说明哪些依赖存在，普通时间说明整批执行是否变快，但二者之间还缺少“运行时哪些指令在等待”的线索。**Source 页**是 NCU 中把源码位置、机器指令及运行统计关联的代码页；**PC（Program Counter）**在这里是机器指令位置，不是源码行号。**PC Sampling** 是只在部分时刻抽取 warp 的指令位置与调度状态，例如正在等一个读数返回，不是逐条指令精确计时。Source 页将动态计数或采样位置接回具体机器指令，正好用于检查等待是否与已画出的依赖相容。如果多链更快却没有相应等待变化，或寄存器/循环代价也明显改变，就应保留其他解释；不能用一个热点百分比代替完整因果链。

**目的与命令：** 确认普通运行通过且本机支持以下 Section 后，从本课目录采一个正式启动。先准备输出目录；已有同名报告时手工改名，不强制覆盖。

```bash
mkdir -p log
ncu --kernel-name-base function -k 'regex:fma_chain' -s 10 -c 1 \
  --section LaunchStats --section SpeedOfLight \
  --section SourceCounters --section InstructionStats \
  --section MemoryWorkloadAnalysis \
  -o log/d_chains1 ./build/lesson09
```

`--kernel-name-base function` 按基础函数名匹配，`-k regex:...` 是正则过滤，`-s 10` 跳过 10 个匹配预热启动，`-c 1` 只采之后一个；`--section` 选择指标组，`-o` 指报告前缀。四链、八链分别手工命名，避免覆盖基线。

命令中的 **LaunchStats** 记录启动规模与资源，**SpeedOfLight** 给整体负载，**SourceCounters** 收集位置相关计数/采样，**InstructionStats** 给指令统计，**MemoryWorkloadAnalysis** 看存储读写。某一项是否真的可用仍取决于设备、NCU 版本和所选采集。

**看什么与如何理解：** 先核对函数实例、N、grid/block 和启动身份，再在 NCU GUI（图形界面）的 Source/SASS 页找执行计数、采样位置及 producer。例如用 `ncu-ui log/d_chains1.ncu-rep` 打开刚才生成的报告，前提是安装了 `ncu-ui`；`.ncu-rep` 是报告文件格式。**Stall** 是某个 warp 暂时不能推进；**Long Scoreboard** 表示等待 L1TEX 相关读写结果的数据依赖，L1TEX 是涉及 L1 缓存及部分读写处理的路径，不等同 DRAM。PC Sampling 是统计抽样；consumer 上等待多，原因可能来自它等候的 producer，不是 consumer 自己算得慢。某行占 50% 样本不等于占总时间 50%，其他 warp 可能仍在发射指令。

**异常检查：** 没报告先查过滤器和工具错误；无源码视图先查源码可访问性与行映射；某指标不可用就记录限制。spill 需要后端 spill 输出、实际 local 指令和相关动态指标交叉支持；local（线程私有地址空间）也可来自数组/栈，寄存器多或出现 local 指令都不自动证明 spill。**Replay（重放）**是 NCU 为采不同指标重复执行；**插桩**是在机器指令中加入记录操作，可能改变运行时间。它们下的耗时不是独立性能基线。

### 补例 B：从搬动矩阵元素认识访存与同步指令

**矩阵转置**交换行列位置；行优先存储先连续保存一行，线性下标是 `row*M+col`，M 为边长。转置不是乘法，而是把输入的第 row 行、第 col 列搬到输出的第 col 行、第 row 列。例如一个 2×2 矩阵 `[[a,b],[c,d]]` 应变成 `[[a,c],[b,d]]`；实际 runner 用 `(i%251-125)*0.125f` 生成输入，所以前四个值是 -15.625、-15.5、-15.375、-15.25，转置后线性排列应为 -15.625、-15.375、-15.5、-15.25。主机生成并上传矩阵、预填输出哨兵（先放特殊值以发现漏写），GPU 搬动元素，主机下载并精确检查每个位置。

tx/ty 是块内横/纵坐标，naive 指同线程直接搬运。这里 block 是 `(32,8)`，合作处理 32×32 区域，每线程沿行方向分四次处理。naive 由同一线程直接读写对应位置；tiled（分块中转）则先把元素写入块内 **shared memory（共享内存）**，这是同块线程共同访问的 SM 上小存储；**全块同步/Barrier** 等规定的参与线程到齐，使下一阶段不读尚未准备好的值，再由另一组线程按转置顺序取走。例如局部元素 `[0][1]` 由 `(tx=1,ty=0)` 装入，却由 `(tx=0,ty=1)` 在输出阶段读出。padding（填充）版只把 shared 每行从 32 个槽扩成 33 个，额外槽不作为矩阵输出。Global 是设备全局地址空间；Load/Store 是读/写，Barrier 是同步指令。Shared 按 bank（存储分组）服务，多个不同地址争用同组需分批服务叫 bank conflict，行距变化可能改变分组映射。这样既能在 SASS 中寻找 global/shared load/store 和 barrier，也能比较多一个槽是否改变 shared 访问行为，而不是继续寻找 FMA 依赖。

拿局部元素 `[0][1]` 继续推导：naive 不需要把数据交给别的线程，但相邻线程的输出地址可能相隔整行；tiled 让数据经 shared 转交，换取输出连续，却新增 shared 指令和一次全块等待。padding 不再改变这种搬运路线，只改变 shared 地址的行跨度。因此静态检查要先区分“新增哪类指令”和“相同指令访问哪里”；仅仅找到 barrier 不说明它是瓶颈，仅仅行跨度变化也不保证速度提高。这里先用尾部输入验搬运语义，再比较机器码，正是为了不把错误漏写误认为优化。

理解上述搬运后，再将 main 的 `example=1`，沿 [matrix_transpose.cuh](../kernels/matrix_transpose.cuh) 阅读三个实现。先用 `matrix_n=65` 核对尾部，固定 N 和 block，分别改 `transpose_variant=0/1/2`，每次显式重编、运行和反汇编。0→1 改了搬运算法，1→2 才是只改 shared 行跨度；预测前一对增加 shared/barrier，后一对主要改变地址步长，但最终指令形式须看当前产物。动态采集要换成真实的 `transpose_naive`/`transpose_tiled` 过滤器，不能沿用 FMA 报告。

### 补例 C：从逐块求和认识 shared 树与 shuffle

**规约/归约（Reduction）**把多个输入合成较少结果，本例是求和；但本例 GPU 只输出每块的局部和，最后由 CPU 汇总。取前三项 -0.375、-0.25、-0.125，和是 -0.75；实际输入按这三个负数、0、三个正数每七项重复。每块 256 线程各读一项，越界者拿零且仍参加合作，线程 0 最后写一个 partial。主机上传输入、分配并预填 partial 数组，GPU 产生 partial，下载后 CPU 逐块核对再汇总。N=65 时只有一个 partial，预期为 -0.625。

shared 版把线程值存入共享数组，以 offset=128、64、…、1 把配对值相加，每层都同步；**shuffle（线程间值交换）**版让一个 warp 内的 32 个线程直接交换寄存器值，例如线程 0 获取线程 16 的部分和再相加，先形成八个 warp 和，再经 shared 和一次块同步交给 warp 0 继续相加。因此本例适合寻找 shared 访问、barrier 与 shuffle 指令的差别，而不是把“同步少”直接等同于“更快”。

例如 shared 树第一层中线程 0 加线程 128 的值，下一层再加线程 64 所代表的子树；每层依赖上一层完成，不能任意去掉同步。shuffle 不是省略这些数学加法，而是把 warp 内的值交换从共享数组转为寄存器交换；跨 warp 汇合仍需要 shared 与块同步。由这个数据流才能提出应观察的差别：shared/barrier 的动态工作可能减少，但交换指令、输入读取和输出 partial 仍在，是否加速还取决于这些工作占多大比例。这里每块输出一个结果，不能把线程 0 写出误解为只有线程 0 在计算。

然后才将 main 的 `example=2`，读 [reduction.cuh](../kernels/reduction.cuh)，先设 n=65 并核对，再固定 n 只切 `shuffle=false/true`，各自重编、运行、反汇编；采集改用 `reduction_shared`/`reduction_shuffle`。观察局部和数量和数值是否相同、同步及交换指令是否按预测变化。若指令变化而时间未改善，可能是当前规模或其他开销占主导，不能用 FMA 的 ILP 结论替代本例分析。
