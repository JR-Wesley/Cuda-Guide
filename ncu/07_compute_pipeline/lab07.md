# 实验 07：运算次数相同，多条独立计算链为什么可能更快？

## 本课要解决的问题

一个人做八道题，如果每题都必须使用上一题答案，就不能提前做下一题；若有四组互不依赖的题，就有机会轮换处理。**计算流水线（pipeline）**把一次运算拆成若干处理步骤，让不同独立运算的步骤重叠，像接力加工；GPU 也需要持续收到可执行的工作。“写了很多乘加”并不等于“算术部件一直忙”。

本课比较 **FMA（融合乘加）**：`fmaf(x,a,b)` 计算 `x*a+b`，乘加后只做一次最终舍入。一次按一乘一加计 2 **FLOPs（浮点运算次数）**，不表示两条机器指令。本课用相同的逻辑 FMA 数，比较一条与多条独立递推链，区分**单条指令结果要等多久、每秒完成多少工作、靠什么隐藏等待**。理论配读：[lec07 第 1～3、8～9 节](lec07.md)。

值得做这个实验，是因为仅用“运算很多”无法决定下一步该优化什么。等待前一条结果时，增加同一条链的长度只会延长任务；增加互不依赖的链才可能提供可交错执行的工作。但 GPU 也能切换到其他线程组，独立链并不总有额外收益。本课把读输入数组的负担拿掉，固定主循环的乘加次数，再观察依赖结构改变后完成同量工作的时间，让这些解释能够被对照检验，而不是把任何提速都归给算力。

先认识本例的执行分工：**kernel** 是 GPU 执行的函数，**线程**是执行它的一份工作实例，每个线程负责一个 `out[i]`，不是只让一个线程做完整数组。线程按 **block（线程块）**分组，同块可协作；所有块组成一次启动的 **grid（网格）**。硬件按每 32 个线程组成 **warp**，其中位置叫 **lane**；当前路径中参与的 lane 不一定满 32 个。FP32 是本例 32 位浮点数 `float`，占 4B，B 是字节、一个字节为 8 bit。后面以 FLOP/s（每秒浮点运算数）和 GFLOP/s（每秒十亿次）比较速率，不能把总次数当速度。

以下是待执行练习与预测，没有填入本次测量值。

## 1. 先用八次 FMA 画出依赖关系

这里的 FMA kernel 不接收一张待处理的输入数组。它的输入是输出长度 N、每线程总乘加次数、乘数和加数，链数则在编译时确定；每个线程用自己的编号生成初值，在内部反复做 `新值=旧值*乘数+加数`，最后只写一个 `out[i]`。它没有把 N 个线程的结果相加，也不需要线程间同步。保留最终输出是为了让计算有可检查的结果，而不是写一个算完便丢弃的循环。

以 N=1、总次数 8 为例，单链从 0.50390625 开始，连续更新八次；四链各有自己的初值，每条只更新两次，最后把四个终值相加。两者都做八次 FMA，却不是同一个数学输出。差别恰好是本课要制造的：单链第 k+1 次必须使用第 k 次的结果，四链中更新第二条不需要第一条刚产生的结果。用最终输出相同来要求两版“公平”反而会误解这个实验。

**主机（Host）**是运行 CPU 代码的一侧，负责分配、提交和检查；**设备（Device）**是 GPU 一侧。`i` 是全局线程编号，`blockIdx.x*blockDim.x+threadIdx.x` 分别用块号×每块线程数+块内编号算出，例如每块 256 线程时块 1 的线程 3 负责 i=259。主机只为 GPU 分配 N 个输出，不上传初值数组；它以 `ceil(N/block)`（向上取整，例如 257/256 需 2 块）个块、每块 block 个线程启动选定链数的 kernel，并传入 1.0001f 和 0.0001f。多启动的线程检查编号后返回。计时结束后主机拷回全部输出，用 CPU 按每条链的相同初值、轮数及末尾求和顺序重新计算，再检查有限性和误差。这样，输出错误与性能变化可以分开判断；无输入数组则减少了大规模全局读取对本课依赖问题的干扰，并不表示执行完全没有存储访问。

**目的：** 理解“链”是数据依赖，不是增加线程数。读 [入口 main.cu](kernels/main.cu)，再读 [fma.cuh](../kernels/fma.cuh) 的 `fma_initial`、`fma_chain` 和 `run_fma`。

入口默认 `n=1<<14`（把 1 左移 14 位，即 16384）、block=256、chains=1、total_fmas_per_thread=1024；没有命令行参数。`Chains` 是模板参数，即编译时确定的链数；小写 chains 是入口传给模板的常量。

先在纸上用线程 i=0、每线程 total=8：第 j 条链初值为 `0.5+(j+1)/256`；线程 i 的初值还加 `i/65536`。每次执行 `acc[j]=fmaf(acc[j],1.0001f,0.0001f)`，最后把所有链加起来写 out[i]。

| Chains | 每链 rounds | 数据依赖形状 | 写出的值 |
|---:|---:|---|---|
| 1 | 8 | x0→x1→…→x8 | 一条链递推后的值 |
| 4 | 2 | 四条各自 x0→x1→x2 的链 | 四条链结果之和 |

例如单链 i=0 初值为 0.50390625，第一次乘加用实数近似为 0.504056640625；实际 FP32 会舍入，不要求手算小数与机器逐位一致。四链初值分别为 0.50390625、0.5078125、0.51171875、0.515625；其输出与单链本来就不同，**不能用两版输出相等作为正确性标准**。

本步无需命令。理解检查：Chains=4、total=8 时循环 rounds 是多少？答案 2，不是 8；每个线程仍只写一个 float。若数出 32 次 FMA，先检查是不是把 total 当成了每链轮数。

## 2. 先分开延迟与吞吐，再定义公平对照

**目的：** 在运行前知道实验究竟能回答什么。

**指令**是机器执行的一次操作，例如将三个输入做乘加；**调度器（Scheduler）**挑选下一条能执行的 warp 指令；**发射（issue）**是它将指令交给执行资源，不表示已经完成。延迟 latency 是一条指令发出后，后继何时能用结果；吞吐 throughput 是一段时间完成多少工作。**周期（cycle）**是硬件时钟的一拍，不直接等于纳秒，换算要知道频率。假设教学流水线结果要等 4 周期、却每周期能接收一条独立指令：单链下一条可能必须等，四条独立链则可能轮换填空。这只是解释模型，不是本机 FMA 延迟测量。

ILP（指令级并行）是在同一线程中准备独立指令，例如 acc0 等结果时可更新 acc1；TLP（线程级并行）是在一组线程等待时运行别的 warp。若其他 warp 已隐藏等待，增加链数未必更快。多链也可能需要更多**寄存器**（线程保存临时值和地址的快速小存储）。GPU 上的 **SM** 是容纳并执行线程的处理单元，**驻留 warp** 已分配到 SM、尚未结束；寄存器有限，单线程用得越多，可能同时容纳的 warp 越少。

**循环展开（unroll）**把多轮循环体复制到机器指令中，减少循环判断并给独立操作重排机会，不是增加算法更新次数。读 `fma_chain` 的循环：内层 `#pragma unroll` 请求展开已知链数，外层 `#pragma unroll 1` 请求不要展开该循环。不同初值、运行时传入的系数和末尾使用全部累加器体现源码意图，但不保证最终 SASS（GPU 机器指令）一定符合设想，后续必须静态检查。

主对照选择 fixed work（固定工作量）：

| 设计 | 固定什么 | 只改什么 | 含义 |
|---|---|---|---|
| 主实验：total=1024 | N=16384、block=256、GPU、编译参数 | Chains=1/4/8 | 每线程总 FMA 不变，每链 rounds=1024/Chains |
| 独立扩展：total=1024*chains | N、block、每链 rounds=1024 | chains | 工作量也随链数增加，不能当等量任务加速 |

**fixed work** 在这里仅固定主循环名义工作量，逻辑是按源码意图计数，而不是声称机器统计完全相同。主实验每次逻辑 FMA FLOPs 为 `2*N*total=33,554,432`，逻辑全局写字节为 `4N=65536`。每线程最后还有 `Chains-1` 次加法，不计入打印的 FMA FLOPs；链数变化还改变循环控制次数，所以**固定 FMA 数不等于完全相同机器工作量**。

每个累加值从产生到最后一次使用之间必须保留，称**活跃区间（live range）**；多链使多个值同时保留，可能增加寄存器压力。寄存器分配放不下或分配策略受限、暂存到其他位置再读回，叫 **spill（溢出）**；通常涉及 **local（线程私有地址空间）**，也可能依工具链使用其他路径。local 不是“函数内声明变量”的同义词，数组不一定放 local。先认识机制，后面的静态检查才知道要找什么。

本步不运行工具。先算 Chains=8 时 rounds=128；若 total 无法整除 Chains，runner 会拒绝执行。吞吐公式为 `FLOPs/(ms*10^6)` GFLOP/s：ms 是程序给出的毫秒数，秒数为 `ms*10^-3`，换成 GFLOP/s 还要除以 `10^9`，合并后分母就是 `ms*10^6`。例如 2,000,000 FLOPs 用 1 ms，结果为 2 GFLOP/s。能解释单位，才使用程序打印的速率。

## 3. 先编译最小核对例，再独立普通运行

**目的：** 验证递推、模板选择和 CPU 参考，不让计时掩盖错误。以下 Bash 命令工作目录为 `cuda/ncu/07_compute_pipeline/`，相对工作区根目录为 `ncu/07_compute_pipeline/`。

未来先检查环境：

```bash
nvidia-smi
nvcc --version
ncu --version
```

`nvidia-smi` 显示设备与驱动（让程序使用 GPU 的系统软件），`nvcc` 是 CUDA 编译器，Toolkit 是含编译器等开发工具的软件包；`ncu` 是 Nsight Compute 的命令行入口。`--version` 查看各自版本；另确认 compute capability（GPU 支持的架构版本）与 Toolkit 支持范围。`nvidia-smi` 的 CUDA 版本并不代表已安装 Toolkit；下文 sm_89 只是架构示例，应替换成设备对应目标。

为对应步骤 1，可先只把入口 n 改为 1，重编核对；然后只把 total 改为 8，再重编核对；最后只改 chains=4，再重编核对。block 保持 256，越界线程立即返回。这是教学核对组，不是性能组，也不是要求本次修改源码。

单独编译：

```bash
mkdir -p build log
nvcc -std=c++17 -O3 -lineinfo -arch=sm_89 kernels/main.cu -o build/lesson07
```

`mkdir -p` 创建目录；`-std=c++17` 选语言版本，`-O3` 优化，`-lineinfo` 保留分析器源码映射，`-arch` 选架构，`-o` 指产物。修改入口或共享头后都要显式重编；编译失败读首个错误，不运行旧产物。

再普通运行：

```bash
./build/lesson07
```

**看什么：** 配置行是否真是本次 N、Chains、total、rounds；预期 `Check: PASS`、`checked=N`、`mismatches=0`。runner 不打印全部 out，但在 CPU 上按同一链数、初值、轮数及求和顺序核对所有 N 项，要求结果不是 NaN（非数值）或正负无穷，且绝对误差不超过 `1e-5+1e-4*abs(reference)`；reference 是 CPU 参考值，abs 是绝对值，`1e-5/1e-4` 分别是 $10^{-5}/10^{-4}$，同时提供小结果的绝对容差和随结果大小变化的容差。若失败，查首个错误、参数与重编状态，不能通过放宽容差来跳过问题。

读 [common.cuh](../kernels/common.cuh)：`CUDA_CHECK` 报告 CUDA 错误；`time_kernel` 做 10 次预热，用 CUDA Event（GPU 时间标记）对 20 次启动计时并取平均，检查启动错误并同步。分配、拷回与 CPU 参考都在计时外；**预热**是先执行若干次，减少首次初始化等影响；**同步**是等 GPU 上相关工作完成后再往下做主机操作，避免把“已提交”误当“已完成”。Event 批量平均是整段时间除以启动次数，可能含提交间隙，不等于单条 FMA 的延迟。N=1 主要用于核对，不拿它声称流水线吞吐。

## 4. 固定逻辑 FMA 数，观察多链是否真的更快

**目的：** 将步骤 2 的模型变成可反驳的假设。

小例只证明八次更新和求和的语义。把每线程总次数扩大到 1024，是为了让递推在任务中占据更明显的部分；把输出扩大到 16384，是为了让多个线程块参与。随后只改链数，才问相同主循环 FMA 数能否更快完成。如果多链提高可执行工作的供给，应有时间或发射活动响应；如果其他 warp 早已填补等待，这个干预就可能几乎无效。这两个方向都属于有用结果，不能预先把“没有加速”当作实验失败。

在入口分次恢复 n=16384、total=1024、chains=1，每次重编并核对；建立主性能组。之后只改 chains：1→4→8，其他条件不变。每版按步骤 3 重编、先 PASS，再多次普通运行，记录平均 kernel 时间的中位数与波动。每次程序先给一个批量均值，再把多次普通运行的这些数排序，**中位数**是居中的值（偶数个样本取中间两项的平均）；同时保留原始值和最小/最大等波动范围，不只挑最快一次。相同工作量下用 `ms_chains1/ms_candidate` 算加速比。

预测是“独立链可能减少等待、提高吞吐”，不是“链数翻四倍就快四倍”。若速度不变，可能 TLP 本来就足够；若变快，也可能部分来自更少的循环控制；若变慢，寄存器与调度代价可能抵消收益。需要后续证据区分。

同一目录先查 NCU（Nsight Compute，kernel 指标分析器）支持的 Section（指标组）：

```bash
ncu --list-sections
ncu --query-metrics
```

再针对 chains=1 采集：

```bash
ncu --kernel-name-base function -k regex:fma_chain -s 10 -c 1 \
    --section LaunchStats --section SpeedOfLight \
    --section ComputeWorkloadAnalysis --section InstructionStats \
    --section SchedulerStats \
    -o log/d_chains1 ./build/lesson07
ncu --import log/d_chains1.ncu-rep --page details
```

`function` 按基础函数名筛模板实例；`-k` 为名称过滤器，`regex:` 表示用正则表达式描述名称模式，此处匹配包含 fma_chain 的名字；`-s 10 -c 1` 跳过 10 次匹配启动、只采随后一次，和预热次数对应。`--section` 指定指标组，`-o` 输出报告；`--import` 读取报告，`--page details` 展示详情。Chains=4/8 各自重编、普通核对后采集，报告手工改为 d_chains4/d_chains8，不能把旧报告当新实例。

下面报告组各司其职：**LaunchStats** 看启动规模/资源，**SpeedOfLight** 看整体计算与存储资源负载，**ComputeWorkloadAnalysis** 看具体计算路径，**InstructionStats** 数机器指令类型，**SchedulerStats** 看调度。FP32 pipe 是执行 FP32 运算的路径；**SM Throughput** 是汇总指标，可能由最繁忙子路径主导，不是所有浮点部件平均。**Eligible** 表示 warp 下一条指令满足发射条件；**Issue Activity** 看发射活跃度；**IPC** 是指令条数/周期数，必须统一发射还是执行、SM 还是调度器、活跃周期（active）还是经过的全部周期（elapsed）。

| 看什么 | 用来回答什么 | 异常先检查 |
|---|---|---|
| LaunchStats 的实例、grid/block、寄存器 | 配置与资源是否真的一致/改变 | 报告名、二进制、编译参数 |
| ComputeWorkloadAnalysis 的 FP32 路径 | 多链是否提高相应计算路径繁忙程度 | 高 SM Throughput 不等于 FP32 峰值达到 |
| SchedulerStats 的 Eligible、Issue Activity | 是否有更多可执行 warp/更持续的发射 | Eligible 是可发射条件，不是总驻留数 |
| InstructionStats 的指令混合、IPC | FMA 与循环控制是否一起变化 | IPC 是每周期指令数，确认按 SM/调度器及 active/elapsed 的口径 |

NCU 可能 replay（重复执行以收集不同指标），其下的 Event 时间不作为独立基线。线程级逻辑 FMA 数也不能直接与 warp 级指令计数对比：一条 warp 指令可让多个活跃 lane 各做一次 FMA。缺失指标记“未采集”，不填零。

## 5. 独立检查机器码，再做规模与资源扩展

**目的：** 确认源码意图确实留在机器指令中，不靠“数组写法”推断寄存器或 spill。

在同一目录，对当前已编译二进制单独执行静态检查（无需启动 kernel）：

```bash
cuobjdump --dump-sass build/lesson07
cuobjdump --dump-resource-usage build/lesson07
```

**静态检查**只读编译产物，不执行 kernel；**动态计数**才说明运行中执行多少次。静态一条循环 FMA 可以动态执行千次。`cuobjdump` 是 CUDA 二进制检查工具；`--dump-sass` 展示实际 GPU 指令，`--dump-resource-usage` 展示资源使用。先找到选中的 fma_chain 实例，查看循环中的乘加与分支、各累加器的寄存器依赖、末尾求和和输出。不要只搜到 FFMA 就断言多链独立：需顺着读写寄存器检查谁依赖谁。读 SASS 时，`FFMA R10,R8,R4,R10` 表示新 R10=R8×R4+旧 R10，第一个寄存器是目标，其后是输入，因此下一次读 R10 有真实先后依赖。具体编号只是读法示例，不是本程序实测。若工具缺失或无法辨认，标明未验证，不虚构寄存器数。

机器码检查用于排除“源码看起来独立，实际生成的指令却不同于预想”的解释，但仍不能单凭静态指令证明运行时瓶颈。接下来分别改变规模和链数，是继续区分两种工作来源：更多输出带来更多 warp，更多链带来同一线程内部的独立指令。二者都可能填补等待，却有不同的资源代价，所以必须拆开实验；固定每链轮数则另回答增加工作后吞吐如何变化，不再回答同量工作是否更快。

然后可各开一组对照，仍用步骤 3 的编译/运行与步骤 4 的采集方法，报告另命名：

- **只改 N：16384→32768。** 固定 chains、block、total；默认 16384/256=64 个 block，大 GPU 可能未填满。若吞吐提高，可能是并发规模改善；若已饱和，工作加倍可能主要让时间加倍。
- **只改 Chains：8→32→64。** 固定 N、block、total=1024；观察寄存器与 occupancy（驻留 warp 数/该 SM 硬件允许的最大 warp 数，例如 32/64=50%，不是管线忙碌率）。spill 是寄存器放不下而溢出到其他存储的情况，不能预设一定出现，也不能把 C++ 局部数组直接当 local memory。需机器码、资源与访存证据，深入方法见第 09 课。
- **fixed rounds 扩展。** 显式设 total=1024*chains，保持每链轮数相同；这是另一种工作量设计，单独记录，不能并入主实验的加速比。

## 6. 总结、验收与记录边界

请不看表回答：① 四链比一链快两倍，能说硬件 FMA 延迟减半吗？不能，测量的是整段工作完成速率。② 链数变多而寄存器上升、occupancy 下降，为什么仍可能快？ILP 收益可能超过 TLP 损失。③ 固定 total 为什么仍不能称机器工作完全一致？循环与末尾求和也变了。能用实际配置、普通时间、指令与调度证据解释，才算完成本课。
