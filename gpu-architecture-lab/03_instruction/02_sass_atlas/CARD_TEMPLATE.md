# 指令分析卡：记录模板与证据要求

这是填写规则，**不是一份已有测量结果**。每个类别页按实际观察到的指令建立小节；同一案例可以关联多个小节，不重复保存源码与日志。不必为每个后缀建立独立文件，也不让通用模板淹没短例子的解释。

## 1. 先写任务与状态

- **问题**：这条指令在当前 kernel 中解决什么具体问题？
- **案例入口**：源码相对路径、函数/模板实例、相关表达式、输入和预期输出。
- **学习前置**：首次遇到的地址、位宽、谓词、mask、scope 等概念就地解释。
- **单变量对照**：改变什么，其他哪些条件保持不变？
- **状态**：规划 / 源码已盘点 / 编译成功 / 静态已观察 / 小规模正确性已验证。分别写，不用一个 PASS 覆盖所有环节。

“未观察到”仅用于实际检查过产物但没有发现目标形式；还没编译应写“尚未检查”，不混用两者。

## 2. 编译与产物身份

记录足以复现本案例的信息，不自动快照或计算内容哈希：

| 字段 | 应填写什么 |
| --- | --- |
| 工具版本 | `nvcc/ptxas/cuobjdump/nvdisasm` 中实际使用者的版本；资料版本另列 |
| 目标 | 完整 `sm_XX` 或含架构后缀的目标；不能只写“支持 Hopper” |
| 编译配置 | 完整命令、工作目录、语言版本、优化、行信息、宏/模板、寄存器限制、是否 RDC/LTO |
| 输入产物 | PTX/cubin/可执行文件的准确路径，目标 kernel 符号；多个镜像时指出选哪一个 |
| 日志 | 对应 `commands/compile`、`commands/static` 的当前配置日志与退出码 |
| 运行条件 | 只有运行时才填 GPU/CC/驱动、launch、输入；交叉编译不写成运行通过 |

若要严格证明“这份 PTX 生成这份 cubin”，在显式编译动作中用 `ptxas` 汇编所保存的 PTX，或保留同一次编译的中间文件及实际命令。分别运行 `nvcc -ptx` 和 `nvcc -cubin` 得到的产物，可以做相同配置的关联阅读，但不能未经核对宣称它们具有严格的直接生成关系。

`-O3` 用于优化构建；`-lineinfo` 保留源行关联而不等同于 `-G` 设备调试。优化后可能重排、融合、消去指令，行号只是定位辅助，不是逐行一一对应证明。按课程需要解释这些选项，不一次引入全部编译链参数。

## 3. 语义与实际指令分开摆

按下面顺序记录一小段足以解释问题的代码，不复制整文件：

1. **CUDA 源码**：输入、地址空间、类型、边界、参与者及输出用途。
2. **实际 PTX**：保留所需参数与寄存器定义、指令片段，链接原文件/日志。引用对应版本 PTX ISA 的具体指令章节与 target 条件。
3. **实际 SASS**：写出函数名、指令偏移、完整 opcode/修饰符、谓词和操作数，并包含必要前后文。链接原始反汇编。
4. **对应关系**：标明一对多、多对一、消失或未知；不能只凭行号或全文件正则命中判断对应。

没有真实产物时只写“目标候选”，不编造 `R0/R2`、偏移或“本机生成如下”的片段。引用官方示例要明确它不是当前源码产物。

## 4. 操作数与数据流

先解释反汇编中实际出现的记号，再画一条能跟踪到输出的链：

| 记号/角色 | 阅读问题 |
| --- | --- |
| `R`、`UR` | 普通/统一寄存器在哪里产生、在哪里消费？统一值与每 lane 值是否被编译器区分？不能单凭字母推断物理管线 |
| `P`、`UP`、`@P`、`@!P` | 哪条指令产生条件？哪些指令受它控制？条件的真实参与 lane 是什么？ |
| `RZ`、`PT` | 目标语法中的零寄存器、恒真谓词怎样参与操作？不将它们算作用户变量 |
| 立即数 | 是普通数值、位移量、字节选择器、布尔真值表，还是暂不清楚的控制字段？ |
| 地址操作数 | 基地址、缩放索引、偏移、宽度与对齐分别是什么？寄存器对/descriptor 形式按实际目标说明 |
| 目的操作数 | 结果写去哪？原子旧值、shuffle 的有效性结果、进位/谓词是否被后续使用？不能默认所有指令第一个参数都是普通数据目的寄存器 |
| 修饰符 | 哪些由官方资料确认，哪些是观察或社区推断？未知就保留原文，不套用另一架构的解释 |

例子对应的必要图只选一种：访存画 lane→字节地址表；`LOP3` 画真值表；`PRMT` 画字节选择；分支画基本块；异步 copy 画发起→完成→消费→允许复用的依赖。

## 5. 功能、管线、延迟、吞吐四列必填

| 项目 | 内容与证据级别 |
| --- | --- |
| 功能语义 | 规范保证、SASS 官方简述、当前数据流解释分别列出；同步写明 scope/order/参与条件 |
| 执行管线 | 有对应架构资料才注明其出处；否则写“未知”或“候选，未验证”，不以 opcode 名称下结论 |
| 延迟 | 默认“未测量：本课只做指令分析”；不能用 kernel 时间、stall 百分比或静态依赖长度填周期数 |
| 吞吐 | 默认“未测量：未开展受控吞吐实验”；不能用指令数/任意时间代替管线吞吐 |
| 架构差异 | 分列实际编译目标和所见形式；仅查到文档支持与实际静态观察分开，未运行目标明确注明 |

每个主要结论标注来源：**规范 / 静态观察 / 小规模运行 / 模型推导 / 社区资料 / 未知**。没有 NCU 数据不影响完成静态分析课。

## 6. 可选 Nsight Compute 观察字段

先写要回答的问题，再选择该工具版本和设备确实提供的 section/metric。下面是观察方向，不是已采集指标或跨版本稳定的 metric 名称：

| 指令类别 | 候选观察内容 | 不能直接推出 |
| --- | --- | --- |
| Memory | Source 指令关联；Memory Workload Analysis 中访问、sector、local/shared 与原子相关统计 | 某条 `LDG` 必然命中某级缓存；local 统计必然全是 spill |
| Address & Integer | Instruction Statistics、Source Counters 的指令执行与活跃线程；有定义依据时再看管线指标 | `IMAD` 的单条延迟；统一与普通数据路径的物理实现 |
| Synchronization | Warp State Statistics、Source Counters 中支持的 barrier/依赖等待采样 | 某一等待比例证明同步正确，或全部等待唯一归因于某条 `DEPBAR` |
| Control Flow | 源指令、分支与线程参与统计，结合输入条件和 CFG | 静态 `BRA` 数量等于动态分歧次数 |
| Data Movement | shuffle/搬运指令统计；设备支持时的 async/TMA 相关统计 | 发出异步指令就一定与计算重叠，或计数等于有效搬运字节 |

实施时先使用 `ncu --list-sections`、`ncu --query-metrics` 查本机可用项目，再在独立 profile 动作中限定一个 kernel 和少量指标。记录**实际 metric 全名、单位、采样/计数含义、报告路径、过滤条件、是否 replay**；replay 是工具为采齐指标可能重复执行负载的机制，不是普通运行基线。没有可靠的逐指令指标时写“没有可直接对应的指标”，不建立虚假的 opcode→counter 一一映射。

本轮该部分统一为“未测量：规划阶段，不做 profiler 采集”。后续权限不足、设备不支持和未安装工具分别写明，不填零，也不借旧记录补齐。

## 7. 课末结论、练习与异常检查

用几句话回答：

- 当前证据已经证明什么？仍然不能证明什么？
- 改一个条件前先预测：输出是否改变，指令是否可能融合/消失？
- 实际不符时，先检查是否读错 kernel/目标、输入是否运行时可知、输出是否被消费、类型/地址空间是否改变，再判断优化原因。
- 小正确性运行的输出与 CPU 参考一致吗？未运行则给原因，不把编译当运行。
- 源码或构建配置改变后，哪些证据需要重做？旧日志只作为旧条件证据，不移花接木。
