## 2. 先确认机器指令

| PTX 操作符 | 本机 load SASS | 本机 store SASS |
| --- | --- | --- |
| 默认 | `LDG.E` | `STG.E` |
| `.ca` / `.wb` | `LDG.E.STRONG.SM` | `STG.E.STRONG.SM` |
| `.cg` | `LDG.E.STRONG.GPU` | `STG.E.STRONG.GPU` |
| `.cs` | `LDG.E.EF` | `STG.E.EF` |
| `.lu` | `LDG.E.LU` | 不适用 |
| `.cv` / `.wt` | `LDG.E.STRONG.SYS` | `STG.E.STRONG.SYS` |

这张表是历史记录中的编译器对 sm_89 的观察，不是跨架构通用映射。尤其不要由机器指令名称里的 `STRONG` 推导出 CUDA C++ acquire/release；本例使用的 PTX cache operators 没有改变内存一致性语义。

最终 6 个 `read_reuse` kernel 均在 `0xe0..0x250` 的回跳区间内包含 8 条 LDG，且加载结果用于下一次加载地址。这使得按圈数计算逻辑访问字节数有实际指令依据。

开发阶段的固定地址版本出现了后端将加载移出循环的优化。相关目录当时以 `VALIDITY.txt` 标记无效；被依赖地址环版本取代后，旧日志及快照已清理，仅保留这段历史说明，其 reuse 耗时和吞吐数字不用于本报告。这个现象说明，PTX 中有循环和 `asm volatile` 仍不足以证明机器码进行了重复访存。

## 3. 地址依赖环：小工作集复用

配置：24 blocks × 256 threads，8 KiB/block，共 192 KiB；每线程 8 节点闭环；2048 圈，即每线程 16,384 次加载。每个 variant 预热 3 次，计时采样 9 次。

| load 提示 | 最小 / 中位 / 最大耗时（ms） | 逻辑 GB/s |
| --- | --- | --- |
| 默认 | 0.324 / 0.337 / 0.409 | 1196.2 |
| `.ca` | 0.329 / 0.343 / 0.374 | 1173.8 |
| `.cg` | 1.969 / 2.036 / 2.077 | 197.8 |
| `.cs` | 0.326 / 0.340 / 0.370 | 1183.9 |
| `.lu` | 1.952 / 2.058 / 2.263 | 195.7 |
| `.cv` | 1.962 / 2.044 / 2.149 | 197.0 |

本次 `.cg` 中位耗时约为 `.ca` 的 5.93 倍，两者范围明显分离。结合小工作集和 `.cg` 绕过 L1 的定义，可以提出“L1 复用减少了依赖加载等待”的解释；**这是与语义一致的推断，并非已经采集到 L1/L2 命中率的证明**。

默认、`.ca` 和 `.cs` 的范围相近，当前数据不足以在三者之间确定稳定赢家。`.cs` 是 evict-first 倾向而非立即驱逐；这个小数据集也没有刻意引入竞争工作集，所以 `.cs` 表现接近 `.ca` 并不矛盾。

`.lu` 在此负载中接近 `.cg`。它的 SASS 是独立的 `LDG.E.LU`，而本例又不断复用被提示为 last-use 的数据。可以确认该提示在这个架构与访问模式下不利，但没有计数器证据去断言具体驱逐时机，也不能因此否定规范中其 global streaming 语义。

`.cv` 组此处访问设备内存。因此这些数据不能用于解释 `.cv` 对系统内存重新取数的效果。上表超过 1000 GB/s 的值也只是重复读取的逻辑吞吐，不能称为这块 GPU 的显存带宽。

64 圈 run 的旧证据已清理，不再引用其耗时或与本表作量化比较。短 kernel 的计时可能受提交、调度和频率波动影响，拉长依赖链是可采用的控制方法，但当前单日志不提供两种圈数的实测对照。

## 4. 大数组顺序读

配置：67,109,012 bytes（64 MiB + 148 bytes），96 blocks × 256 threads，工作集约为 L2 的两倍。数值来自同一份 2048 圈运行记录中的 streaming 部分；圈数参数不改变 streaming kernel。

| load 提示 | 最小 / 中位 / 最大耗时（ms） | 逻辑 GB/s |
| --- | --- | --- |
| 默认 | 0.293 / 0.311 / 0.338 | 216.0 |
| `.ca` | 0.294 / 0.309 / 0.344 | 217.4 |
| `.cg` | 0.291 / 0.309 / 0.364 | 217.1 |
| `.cs` | 0.207 / 0.220 / 0.234 | 305.0 |
| `.lu` | 0.221 / 0.309 / 0.321 | 217.1 |
| `.cv` | 0.292 / 0.310 / 0.314 | 216.7 |

保留的这次运行中，`.cs` 的中位耗时约为默认加载的 71%，其范围也与大部分变体分开。可以把 `.cs` 作为这个顺序读取负载值得继续调查的候选，但已删除的 64 圈记录不再作为重复验证依据。

不能进一步断言“提升来自保护其他热点数据”，因为此测试没有第二个热点数据集；也不能由时间反推 L2 命中率或 DRAM bytes。`.lu` 与 `.cs` 的 SASS 不同，在这个 kernel 上的耗时也不同，规范层面的 streaming 提示并不要求两者具有相同性能。

这里的约 305 GB/s 是逻辑有效读吞吐，包含缓存、访问合并和计算的综合影响。没有显式清空缓存或物理流量计数，不能将其直接当作实际 DRAM 带宽。

## 6. Mapped 系统内存

两轮 CPU 初始化分别使用不同 generation；默认及全部 5 个 load hints 均读出正确 checksum。默认及全部 4 个 store hints 写入后，CPU 在 kernel 完成同步之后逐元素校验成功。

因此 `.cv` 和 `.wt` 已经在 mapped host memory 上实际执行，不只是编译了对设备内存的指令。但本组仅做功能校验，没有给出 mapped 内存性能、每次 L2 invalidation 或系统总线事务的测量。其他提示同样通过，原因是程序本身满足访问顺序与完成同步要求。

## 7. 能据此做出的判断

本例展示了三个独立层面的证据：PTX/SASS 确认实际指令；数据检查确认合法顺序下结果正确；采样确认特定负载下的时间差异。它们共同支持本机现象，却不能代替缺失的缓存命中率和流量计数。

在这块 GPU 上，可优先把 `.ca` 作为小工作集依赖复用的基线，把 `.cs` 作为此顺序读取负载的候选，并保留默认 store 作为写入基线。更换工作集、并发度、架构或编译器后应重新验证。无论选择哪个提示，线程间数据发布仍需使用正确的同步协议。
